    Урок 4a: Проектирование интерфейса песочницы

    До сих пор инструменты read, grep и bash знали слишком много о среде выполнения. read импортировал readFileSync из Node.js, bash вызывал execSync. Это работало, пока агент выполнялся на локальной машине. Но настоящий каркас должен уметь запускать агента где угодно: на локальной машине, в in-memory файловой системе, в облачной виртуальной машине. Если каждый инструмент завязан на конкретную среду, то смена среды означает переписывание всех инструментов.

    В этом уроке мы спроектируем единый минимальный интерфейс песочницы, за которым спрячутся все реализации.

    Проблема

    Посмотри, как выглядит инструмент, завязанный на локальную среду:

    const read = tool({
  description: "...",
  execute: async ({ path }) => {
    const content = readFileSync(resolve(cwd, path), "utf-8"); // ← завязан на Node.js
    return content;
  },
});

const bash = tool({
  description: "...",
  execute: async ({ command }) => {
    const stdout = execSync(command, { cwd, encoding: "utf-8" }); // ← завязан на execSync
    return stdout;
  },
});

    Проблемы такого подхода:

    1. Среда зашита в инструмент. Чтобы запустить агента в облачной песочнице, надо заменить readFileSync на сетевой вызов, а execSync — на API виртуальной машины. В каждом инструменте отдельно.
    2. Нет единой точки контроля. Где хранится рабочая директория? Где освобождаются ресурсы при остановке? Где информация о сроке жизни песочницы? Всё размазано по инструментам.
    3. Смешение ответственности. Инструмент должен отвечать за «как инструмент выглядит для модели», а не за «как выполнить команду в конкретной среде».

    Вывод: нужен контракт, который отделяет «что инструменты делают» от «где они это делают». Этот контракт и есть интерфейс песочницы.

    Решение с кодом

    Минимальный async-интерфейс, за которым прячутся все реализации:

    interface Sandbox {
  type: string;
  workingDirectory: string;
  readFile(path: string): Promise<string>;
  exec(command: string): Promise<{ stdout: string; exitCode: number }>;
  stop(): Promise<void>;
  expiresAt?: number;                                   // только для cloud
  snapshot?(): Promise<{ snapshotId: string }>;         // только для cloud
}

    Разберём каждое поле:

    Поле Назначение Почему именно так
    type Метка реализации: "local", "just-bash", "cloud" Промпт и логика знают, где работает агент
    workingDirectory Где работает агент Инструменты и промпт берут путь отсюда, а не из глобальной переменной
    readFile(path) Прочитать файл Единая точка чтения — реализация решает, как именно
    exec(command) Выполнить команду Возвращает {stdout, exitCode}, а не бросает исключение
    stop() Освободить ресурсы Обязателен — облачная ВМ должна быть закрыта
    expiresAt? Срок жизни (только cloud) У локальной песочницы срока нет
    snapshot?() Снимок состояния (только cloud) У локальной ФС смысла делать снимок нет

    Все методы async

    Ключевое решение: все методы возвращают Promise, даже если реализация под капотом синхронная.

    readFile: async (p) => readFileSync(resolve(dir, p), "utf-8"),
//              ^^^^^ синхронная реализация, обёрнута в async

    Почему это важно:

    • Облачный бэкенд реально async. Сетевые вызовы к виртуальной машине — это await vm.files.read(...). Если локальная реализация возвращает строку, а облачная — Promise, сигнатуры расходятся, и каждый вызов превращается в гадание «надо ли await?».
    • Единая сигнатура = единый код. Инструменты вызывают await sandbox.readFile(...) и не знают, синхронно оно внутри или нет. Это и есть смысл интерфейса.

    Несогласованные сигнатуры между реализациями — бардак. Async-везде убирает класс ошибок, связанных с «забыл await».

    Инструменты рефакторятся

    После введения интерфейса инструменты перестают знать о среде. Сравни до и после:

    До (завязан на Node.js):

    execute: async ({ path }) => {
  return readFileSync(resolve(cwd, path), "utf-8");
}

    После (работает с любой реализацией):

    const read = tool({
  description: "...",
  execute: async ({ path }) => {
    return sandbox.readFile(path);   // sandbox внедрён извне
  },
});

const bash = tool({
  description: "...",
  execute: async ({ command }) => {
    const { stdout } = await sandbox.exec(command);
    return stdout || "(no output)";
  },
});

    Инструмент получает sandbox извне (внедрение зависимости). Сам он ничего не знает про readFileSync или execSync — только про контракт Sandbox.

    Опциональные методы и честность контракта

    expiresAt и snapshot помечены ? (опционально) — они есть только у облачной песочницы. Это честный контракт: интерфейс не заставляет локальную реализацию притворяться, что у неё есть срок жизни или снимки.

    Потребитель интерфейса должен проверять наличие:

    if (sandbox.snapshot) {
  const { snapshotId } = await sandbox.snapshot();
}

    Паттерн «опциональные методы, проверяемые перед вызовом» — стандартный способ выразить «возможности, которые есть не у всех реализаций».

    Ключевые выводы

    • Единый интерфейс отделяет «что инструменты делают» от «где они это делают».
    • Минимальный набор: type, workingDirectory, readFile(), exec(), stop() + опциональные expiresAt? и snapshot?().
    • Все методы async — потому что облачный бэкенд реально async, а несогласованные сигнатуры порождают бардак.
    • Инструменты рефакторятся с readFileSync → sandbox.readFile и execSync → sandbox.exec, получая песочницу через внедрение зависимости.
    • Опциональные методы честно выражают возможности, которые есть не у всех реализаций; потребитель проверяет их наличие.

    Попробуй сам

    1. Определи интерфейс Sandbox в своём коде и заставь TypeScript показать ошибку там, где инструменты всё ещё вызывают readFileSync/execSync напрямую.
    2. Напиши заглушку (stub) реализации Sandbox с фейковыми файлами в памяти — и проверь, что инструменты работают с ней без изменений.
    3. Добавь в интерфейс метод writeFile(path, content) и подумай, почему в минимальной версии его нет (какие инструменты пишут файлы, а какие нет).
    4. Проверь контракт на честность: реализуй локальную песочницу без snapshot и убедись, что код с проверкой if (sandbox.snapshot) не падает.
