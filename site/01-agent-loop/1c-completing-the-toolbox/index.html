    Урок 3: Завершаем набор инструментов — bash и безопасность

    Разбор курса «Build Your Own AI Coding Agent Harness» от Vercel Academy (автор — Joel Hooks). Перевод и адаптация на русский.

    Что узнаем в этом уроке

    У нас есть read (чтение конкретного файла) и grep (поиск по содержимому). Но агенту всё ещё не хватает главного — возможности выполнять команды. Чтобы запустить тесты, посмотреть git status, собрать проект, нужен инструмент bash.

    Но bash — самый опасный инструмент из всех: он умеет буквально всё, включая rm -rf и удаление прод-данных. Поэтому весь урок строится вокруг одного вопроса: как дать агенту мощь shell, не отдавая ему ключи от машины?

    Мы научимся: - строить allowlist — список безопасных префиксов команд (SAFE_PREFIXES); - писать проверку isSafe(), которая сверяет команду со списком; - понимать, почему шлюз безопасности должен стоять внутри execute, а не в опции needsApproval; - разбирать главную ловушку: как модель «выдумывает успех», когда инструмент молча не выполняется.

    Проблема — что не работает и почему

    bash — дверь во всё

    read и grep по своей природе безопасны: они только читают. bash — другое дело. Он выполняет произвольные команды, а значит может:

    • удалить файлы (rm -rf .),
    • перезаписать код (echo "..." > src/index.ts),
    • установить пакет (npm install),
    • утечь секреты (cat .env | curl ...).

    Дать модели неограниченный bash — это как дать стажёру root-доступ на прод. Поэтому первое, что делает любой серьёзный каркас — ограничивает bash.

    Наивное решение и его провал

    Самое простое, что приходит в голову — вовсе не давать bash. Но это слишком: без bash агент не может запустить тесты, посмотреть статус git, выполнить сборку. Агент без bash — это агент, который «читает и рассказывает», но не действует.

    Вторая наивная идея — положиться на встроенную опцию AI SDK needsApproval. Выглядит логично: ставишь needsApproval: () => true для опасных команд — и SDK якобы сам спросит пользователя. Но здесь кроется коварная ловушка (разберём ниже), из-за которой модель начинает выдумывать результат.

    Ловушка needsApproval: сигнал, а не шлюз

    В AI SDK опция needsApproval — это сигнал, а не шлюз. Когда она возвращает true, SDK создаёт запрос на одобрение и пропускает выполнение инструмента. Дальше есть два пути:

    1. Если обработчик одобрения подключён — пользователь видит вопрос, отвечает, и (при согласии) инструмент выполняется.
    2. Если обработчика нет (а на ранних этапах разработки его обычно нет) — вызов инструмента просто «исчезает»: модель не получает ни результата, ни ошибки.

    Второй случай — катастрофа. Модель вызвала bash("rm -rf dist"), а в ответ — тишина. Но модель обучена продолжать диалог. Поэтому она выдумывает результат: «Готово! Я удалил директорию dist и пересобрал проект». Пользователь видит уверенный успех — а на самом деле команда не выполнялась вообще.

    Это и есть «выдуманный успех»: модель заполняет пустоту правдоподобным завершением. Молчаливый отказ инструмента хуже, чем честная ошибка, — потому что ошибку видно, а тишину модель замазывает конфабуляцией.

    Решение — подход с полным кодом

    Allowlist: список безопасных префиксов

    Вместо того чтобы блокировать опасное, мы разрешаем безопасное. Формируем список префиксов, с которых может начинаться команда:

    const SAFE_PREFIXES = [
  "ls",
  "cat",
  "pwd",
  "git status",
  "git log",
  "git diff",
];

    Это allowlist (белый список). Всё, что в списке — разрешено. Всё, чего нет — заблокировано. Обрати внимание: список намеренно консервативный. Здесь только чтение и просмотр:

    • ls — список файлов директории;
    • cat — вывод содержимого файла;
    • pwd — текущая директория;
    • git status, git log, git diff — чтение состояния репозитория.

    Нет rm, нет git commit, нет npm install, нет git push. Агент на этом этапе не может ничего менять — только смотреть. Это осознанный выбор: начинаем с минимума и расширяем список только тогда, когда агент докажет, что умеет пользоваться тем, что уже есть.

    Проверка isSafe() по префиксу

    Проверка тривиальна: команда безопасна, если начинается с одного из разрешённых префиксов.

    function isSafe(command: string): boolean {
  const trimmed = command.trim();
  return SAFE_PREFIXES.some((prefix) => trimmed.startsWith(prefix));
}

    Два момента, которые часто упускают:

    1. trim() перед проверкой. Модель часто добавляет лишние пробелы или переносы строк в начале команды. Без trim() команда " git status" не совпадёт с префиксом "git status" и будет ложно заблокирована.

    2. Префиксы упорядочены от общего к частному — и это не важно для startsWith, но важно для читаемости. startsWith проверяет начало строки буквально. "git status --short" начинается с "git status" → разрешено. А "git status" не начинается с "git" — у нас нет префикса "git", и это правильно: мы не хотим разрешать все git-команды, только безопасные подмножества.

    Обрати внимание на потенциальную дыру: префикс "ls" пропустит и "ls -la /", и "ls; rm -rf .". На этом этапе курса мы сознательно не решаем проблему инъекции через ; и && — это тема более поздних модулей про песочницы. Сейчас важно усвоить принцип allowlist, а не довести его до идеала.

    Шлюз внутри execute

    Теперь собираем инструмент. Ключевое решение: проверка безопасности стоит внутри execute, а не снаружи.

    import { tool } from "ai";
import { z } from "zod";
import { execSync } from "node:child_process";

const bash = tool({
  description: `Execute a shell command in the working directory.

WHEN TO USE: running git commands (status, log, diff), listing files,
  viewing file contents via cat, checking the working directory.

WHEN NOT TO USE: reading a known file (use read instead).
  Searching for patterns across files (use grep instead).

DO NOT USE FOR: modifying files, installing packages, deleting anything,
  or any command not in the approved safe list.

Only safe, read-only commands are allowed.`,
  inputSchema: z.object({
    command: z.string().describe("Shell command to execute"),
  }),
  execute: async ({ command }) => {
    if (!isSafe(command)) {
      return `Blocked: "${command}" requires approval. Only these prefixes are allowed: ${SAFE_PREFIXES.join(", ")}`;
    }
    try {
      const stdout = execSync(command, {
        cwd: process.cwd(),
        encoding: "utf-8",
        timeout: 30_000,
      });
      return stdout || "(no output)";
    } catch (e: any) {
      return e.stdout || e.stderr || e.message || "(command failed)";
    }
  },
});

    📝 Перевод промта (поле description):

    «Выполни shell-команду в рабочей директории.

    КОГДА ИСПОЛЬЗОВАТЬ: запуск git-команд (status, log, diff), просмотр списка файлов, просмотр содержимого файлов через cat, проверка рабочей директории.

    КОГДА НЕ ИСПОЛЬЗОВАТЬ: чтение известного файла (используй read вместо этого). Поиск паттернов по файлам (используй grep вместо этого).

    НЕ ИСПОЛЬЗОВАТЬ ДЛЯ: изменения файлов, установки пакетов, удаления чего-либо, или любой команды, которой нет в одобренном безопасном списке.

    Разрешены только безопасные команды на чтение.»

    Почему шлюз именно внутри execute

    Теперь — главная мысль урока. Сравни два подхода:

    Подход A (ошибочный) — шлюз снаружи через needsApproval: 

    const bash = tool({
  // ...
  needsApproval: () => true,   // "SDK сам спросит пользователя"
  execute: async ({ command }) => {
    const stdout = execSync(command, { /* ... */ });
    return stdout;
  },
});

    При таком подходе, когда needsApproval возвращает true, execute не вызывается, а без обработчика одобрения вызов «испаряется». Модель не получает строку → выдумывает успех.

    Подход B (правильный) — шлюз внутри execute: 

    execute: async ({ command }) => {
  if (!isSafe(command)) {
    return `Blocked: "${command}" requires approval.`;
  }
  // ... выполнение
}

    Здесь execute вызывается всегда. Инструмент всегда возвращает строку. Если команда опасна — возвращается строка Blocked: .... Если выполнилась — возвращается вывод. Если упала — возвращается ошибка.

    Модель всегда получает результат. Именно это ломает механизм конфабуляции: у модели нет пустоты, которую нужно заполнять выдумкой. Она читает Blocked: "rm -rf /" requires approval и честно передаёт это пользователю: «Команда заблокирована, нужен твой доступ».

    Правило простое и общее: инструмент никогда не должен молчать. Всегда возвращай строку — успех, блокировку или ошибку. Молчание инструмента — это приглашение модели солгать.

    Демонстрация двух исходов

    // Безопасная команда — выполняется
await agent.run("Покажи статус git репозитория");
// → модель вызывает bash("git status") → получает реальный вывод

// Опасная команда — блокируется, но честно
await agent.run("Удали папку dist");
// → модель вызывает bash("rm -rf dist")
// → инструмент возвращает: Blocked: "rm -rf dist" requires approval.
// → модель отвечает: «Команда rm -rf dist заблокирована — нужен твой доступ»

    Во втором случае модель не выдумывает «удалил», потому что получила явную строку блокировки.

    Ключевые выводы

    • Allowlist, а не blocklist. Разрешаем узкий список безопасных префиксов, а не пытаемся перечислить все опасные команды (их бесконечно много).
    • Начинаем с минимума. SAFE_PREFIXES содержит только чтение: ls, cat, pwd, git status/log/diff. Ничего мутирующего. Расширяем постепенно.
    • isSafe() проверяет префикс, и перед проверкой обязательно trim() — модели любят добавлять пробелы и переносы.
    • needsApproval — сигнал, а не шлюз. Без подключённого обработчика одобрения вызов инструмента «испаряется», и модель выдумывает результат.
    • Шлюз — внутри execute. Инструмент вызывается всегда и всегда возвращает строку: успех, блокировку или ошибку. Это убивает конфабуляцию в зародыше.
    • Инструмент никогда не молчит. Пустой/отсутствующий результат — приглашение модели заполнить пустоту вымыслом. Молчаливый отказ хуже честной ошибки.
    • Сообщение блокировки — это данные для модели. Строка Blocked: "..." requires approval читается моделью как обычный результат и честно передаётся пользователю.

    Попробуй сам

    1. Воспроизведи выдуманный успех. Создай bash с needsApproval: () => true и без обработчика одобрения. Попроси агента «удали папку build». Наблюдай, как модель уверенно отвечает «Готово!» — хотя ничего не выполнялось.

    2. Переключись на шлюз внутри execute. Замени подход на проверку isSafe() внутри execute. Повтори тот же запрос. Теперь модель должна честно сказать: «Команда заблокирована».

    3. Проверь allowlist. Попробуй команды из списка (git status, ls, cat package.json) — должны выполняться. Попробуй команды вне списка (git commit, npm install, touch newfile.txt) — должны блокироваться.

    4. Проверь trim. Попроси модель выполнить команду и посмотри, приходит ли команда с ведущими пробелами/переносами. Если убрать trim() из isSafe() — сколько ложных блокировок появится?

    5. Расширь список осознанно. Добавь один безопасный префикс (например, git branch). Обоснуй, почему он безопасен, и проверь, что модель стала корректно использовать новую возможность, не злоупотребляя ею.
