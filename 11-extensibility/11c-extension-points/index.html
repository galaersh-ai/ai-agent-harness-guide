    Урок 11c: Точки расширения — событийная шина

    Реестр инструментов отвечает на вопрос «какие инструменты существуют». Но есть задачи, которые не принадлежат ни одному инструменту: логировать каждый вызов, блокировать запись в защищённые файлы, инжектировать промпт перед сжатием контекста, делать автокоммит при завершении. Для них нужен другой механизм — событийная шина (event bus).

    Проблема

    Сквозные заботы (cross-cutting concerns) не укладываются в модель «инструмент с описанием и схемой». Если зашивать их в каждый инструмент — получишь дублирование. Если в системный промпт — они размоются и потеряют гарантию выполнения. Нужен способ подписаться на моменты жизни сессии и реагировать на них, не трогая ни инструменты, ни промпт.

    Решение с кодом

    Пять событий жизненного цикла

    type LifecycleEvent =
  | "session_start"             // сессия началась
  | "tool_call"                 // агент собирается вызвать инструмент
  | "tool_result"               // инструмент вернул результат
  | "session_before_compact"    // перед сжатием контекста
  | "session_shutdown";         // сессия завершается

interface EventResult {
  block?: boolean;              // прервать цепочку / заблокировать вызов
  reason?: string;
  modify?: Record<string, unknown>;  // изменить данные для следующих обработчиков
}

interface EventBus {
  on(event: LifecycleEvent, handler: (data: any) => Promise<EventResult | void> | EventResult | void): void;
  emit(event: LifecycleEvent, data: any): Promise<EventResult[]>;
}

    Пять событий покрывают весь жизненный цикл сессии: от старта до завершения, с точками до и после каждого вызова инструмента.

    Четыре примера расширений

    1. Логирование каждого вызова инструмента (handler ничего не возвращает — pass-through):

    bus.on("tool_call", async ({ toolName, input }) => {
  console.error(`[${new Date().toISOString()}] ${toolName}: ${JSON.stringify(input)}`);
});

    2. Блокировка записи в защищённые файлы (handler возвращает block: true):

    const PROTECTED = [".env", "package-lock.json"];

bus.on("tool_call", async ({ toolName, input }) => {
  if (toolName === "write" && PROTECTED.some((p) => input.path.endsWith(p))) {
    return { block: true, reason: `${input.path} is protected by policy.` };
  }
});

    3. Инъекция safety-промпта перед компактизацией (handler возвращает modify):

    bus.on("session_before_compact", async () => {
  return {
    modify: {
      customInstructions:
        "Preserve all safety constraints and approval rules across compaction.",
    },
  };
});

    📝 Комментарий переводчика:

    Событие session_before_compact срабатывает перед сжатием контекста. Handler возвращает модифицированный промпт: «Сохрани все ограничения безопасности и правила одобрения при сжатии». Это важно: после сжатия контекста агент может «забыть» свои guardrails, и инъекция напоминает их заново.

    4. Автокоммит при завершении (handler выполняет действия в песочнице):

    bus.on("session_shutdown", async ({ sandbox }) => {
  const { stdout } = await sandbox.exec("git status --porcelain");
  if (stdout.trim()) {
    await sandbox.exec(`git add -A && git commit -m "WIP: auto-save"`);
  }
});

    Правило цепочки

    Несколько обработчиков на одно событие выполняются в порядке регистрации. Каждый результат определяет судьбу цепочки:

    async function emit(event: LifecycleEvent, data: any): Promise<EventResult[]> {
  const results: EventResult[] = [];
  for (const handler of handlers[event] ?? []) {
    const result = await handler(data);
    results.push(result ?? {});

    // block: цепочка прерывается, вызов блокируется
    if (result?.block) break;

    // modify: применяется — следующий обработчик видит изменённые данные
    if (result?.modify) data = { ...data, ...result.modify };

    // void (ничего не вернул): продолжаем со следующим обработчиком
  }
  return results;
}
    Результат обработчика Что происходит
    block: true Цепочка прерывается, вызов блокируется
    modify Модификация применяется, следующий обработчик видит изменённые данные
    ничего (void) Цепочка продолжается со следующим обработчиком

    Именно это правило делает шину одновременно гибкой и предсказуемой: обработчики могут наблюдать (void), изменять (modify) или прерывать (block) — и порядок их регистрации определяет приоритет.

    Сравнение с реестром инструментов

    Tool Registry Event Bus
    Вопрос «какие инструменты существуют?» «что происходит в моменты жизни сессии?»
    Единица инструмент (имя + описание + схема) обработчик события
    Пример read, grep, bash логирование, блокировка, автокоммит
    Когда подключать новый инструмент для модели сквозная политика/наблюдение

    Реестр — для возможностей (что агент умеет делать). Шина — для политик (какие правила действуют всегда). Вместе они — два ортогональных механизма расширения, покрывающих почти всё.

    Ключевые выводы

    • Событийная шина = 5 событий: session_start, tool_call, tool_result, session_before_compact, session_shutdown.
    • Четыре примера расширений: логирование (void), блокировка файлов (block), инъекция промпта (modify), автокоммит (действие в песочнице).
    • Правило цепочки: block прерывает, modify применяет (следующий обработчик видит изменения), void продолжает.
    • Порядок регистрации = приоритет: обработчики выполняются по очереди, ранние могут заблокировать поздних.
    • Шина — для политик, реестр — для возможностей. Два ортогональных механизма расширения.

    Попробуй сам

    1. Подпишись на tool_call и логируй каждый вызов. Убедись, что handler ничего не возвращает (void) и цепочка продолжается.
    2. Добавь блокировку записи в .env через block: true. Убедись, что запись блокируется, а вызовы других файлов — нет.
    3. Подпишись на session_before_compact с modify и проверь, что инжектированный промпт доходит до сжатия контекста.
    4. Добавь автокоммит на session_shutdown и проверь, что при наличии изменений создаётся коммит, при отсутствии — нет.
    5. Зарегистрируй два обработчика на tool_call: первый логирует, второй блокирует .env. Убедись, что порядок регистрации определяет, увидит ли второй обработчик вызов после первого.
