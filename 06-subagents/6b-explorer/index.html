    Урок 6b: Explorer — исследователь только на чтение

    Explorer — первый из двух типов субагентов. Его работа — исследовать и доложить, ничего не меняя. Он дешёвый, быстрый и одноразовый: создаётся под каждый вызов и выбрасывается вместе со своим контекстом. Именно благодаря этой одноразовости он решает проблему загрязнения контекста у родителя.

    Проблема

    Родителю нужно понять структуру кода: где определяется функция, кто её вызывает, какие есть тесты. Если родитель читает всё это сам, каждый файл остаётся в его контексте навсегда. К концу исследования родитель уже «отравлен» результатами чтения, а ему ещё предстоит планировать и принимать решения.

    Кроме того, исследование — это не одно чтение. Это цикл: прочитал → понял, что нужно ещё → прочитал ещё. Такой цикл на «дорогой» модели (Sonnet/Opus) сжигает деньги впустую: для поиска импортов не нужна модель, умеющая рассуждать об архитектуре.

    Решение с кодом

    Explorer — это ToolLoopAgent с тремя ключевыми свойствами:

    1. Только чтение: инструменты read + grep. Никакого bash, никакой записи.
    2. Быстрая модель: anthropic/claude-haiku-4-5 — дешёвая и быстрая, для поиска и чтения её достаточно.
    3. Жёсткий бюджет: stepCountIs(5) — максимум 5 шагов, дальше он обязан выдать отчёт.
    import { ToolLoopAgent, stepCountIs } from "ai";

function buildExplorer(sandbox, parentTools) {
  return new ToolLoopAgent({
    model: "anthropic/claude-haiku-4-5",       // быстрая и дешёвая
    instructions: `You are an explorer agent. Investigate and report back concisely.
    Working directory: ${sandbox.workingDirectory}
    You have read and grep tools only. You cannot modify files or run commands.
    Gather the requested information and return a concise report.`,
    tools: {
      read: parentTools.read,
      grep: parentTools.grep,
    },
    stopWhen: stepCountIs(5),                  // жёсткий лимит в 5 шагов
  });
}

    📝 Перевод промта (Explorer):

    «Ты — агент-исследователь. Исследуй и дай краткий отчёт. Рабочая директория: … У тебя есть только инструменты read и grep. Ты не можешь изменять файлы или запускать команды. Собери запрошенную информацию и верни краткий отчёт.»

    Создаётся на каждый вызов — свежий контекст

    Ключевая деталь: Explorer не переиспользуется. Каждый вызов инструмента task создаёт новый экземпляр ToolLoopAgent:

    // НЕ так — переиспользование отравляет контекст результатами прошлых исследований
// const sharedExplorer = buildExplorer(...);

// А так — каждый вызов получает чистый лист
async function runSubagent(type, agent, description) {
  // agent создан заново в createTaskTool.execute → контекст пуст
  const result = await agent.generate({ prompt: description });
  return result.text;
}

    Новый агент = новый контекст = ноль результатов прошлых исследований в памяти. Родитель получает только сжатый текстовый отчёт, а не 20 прочитанных файлов.

    Ошибки возвращаются как строки

    Субагент не должен ронять родителя исключением. Любая ошибка — перехватывается и возвращается строкой, которую родитель прочитает как обычный результат:

    async function runSubagent(type, agent, description) {
  try {
    const result = await agent.generate({ prompt: description });
    return result.text;
  } catch (error) {
    // Ошибка возвращается строкой, а не бросается наружу.
    // Родитель увидит её как результат и сможет отреагировать.
    return `${type} subagent failed: ${error instanceof Error ? error.message : String(error)}`;
  }
}

    Почему строка, а не исключение: если субагент бросит исключение, родительский цикл ToolLoopAgent может прерваться целиком. Строка же попадает в контекст родителя как обычный результат вызова инструмента — родитель может решить: повторить, уточнить задачу или сделать сам.

    Полный код: createTaskTool с explorer-веткой

    Вот как Explorer подключается к инструменту task, который вызывает родитель:

    import { tool } from "ai";
import { z } from "zod";

function createTaskTool(sandbox, parentTools) {
  return tool({
    description: `Delegate work to a subagent.
      Explorer (default): read-only research with a fast model.
      Executor: implementation with a stronger model and delegated trust on bash.
      WHEN TO USE: research across many files (explorer),
        bulk implementation (executor).
      WHEN NOT TO USE: ambiguous requirements (use askUser),
        architectural decisions (the parent decides).`,
    inputSchema: z.object({
      description: z.string().describe("What the subagent should do"),
      subagentType: z.enum(["explorer", "executor"]).default("explorer"),
    }),
    execute: async ({ description, subagentType }) => {
      // Explorer-ветка: новый агент, только чтение, 5 шагов
      const agent = subagentType === "executor"
        ? buildExecutor(sandbox, parentTools)
        : buildExplorer(sandbox, parentTools);
      return runSubagent(subagentType, agent, description);
    },
  });
}

    📝 Перевод промта (описание инструмента task):

    «Делегируй работу подагенту. Explorer (по умолчанию): исследование только на чтение с быстрой моделью. Executor: реализация с более сильной моделью и делегированным доверием на bash.

    КОГДА ИСПОЛЬЗОВАТЬ: исследование множества файлов (explorer), массовая реализация (executor).

    КОГДА НЕ ИСПОЛЬЗОВАТЬ: неоднозначные требования (используй askUser), архитектурные решения (родитель решает сам).»

    Почему именно Haiku и 5 шагов

    Параметр Значение Обоснование
    Модель claude-haiku-4-5 Исследование — это поиск и чтение, а не рассуждение. Haiku делает это быстро и в разы дешевле Sonnet.
    Инструменты read + grep Для исследования этого достаточно. Отсутствие bash/записи — защита от случайных модификаций.
    Лимит шагов 5 Достаточно, чтобы прочитать 3–5 файлов и выдать отчёт. Не даёт «уйти в разгул».

    Ключевые выводы

    • Explorer = read + grep + Haiku + 5 шагов. Четыре ограничения, каждое осмысленно.
    • Создаётся на каждый вызов. Новый агент = свежий контекст. Результаты прошлых исследований не накапливаются.
    • Ошибки возвращаются строками. Субагент никогда не роняет родителя исключением — родитель видит ошибку как обычный результат и решает, что делать.
    • Родитель получает отчёт, а не дамп. 20 прочитанных файлов схлопываются в один сжатый текст.
    • Только чтение — это фича. Explorer физически не может ничего сломать, потому что у него нет инструментов для записи.

    Попробуй сам

    1. Вызови Explorer-а с задачей «найди все использования функции formatDate и опиши, в каких файлах она вызывается». Проверь, что он использует только read и grep.
    2. Попробуй дать Explorer-у задачу на 10+ файлов — увидишь, как лимит в 5 шагов заставляет его выдать отчёт раньше, чем он прочитает всё. Это ожидаемо: для глубокого исследования разбей задачу на несколько вызовов.
    3. Добавь в runSubagent логирование: сколько шагов реально сделал Explorer до остановки. Сравни с лимитом.
    4. Намеренно вызови ошибку (например, пустой description) и убедись, что родитель получает строку-ошибку, а не падает.
    5. Замени Haiku на Sonnet в Explorer-е и замерь разницу в стоимости и качестве отчёта. Для большинства исследовательских задач разница в качестве будет минимальной, а в цене — заметной.
