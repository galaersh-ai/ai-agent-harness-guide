# Урок 9c: Контракт верификации — честность вместо покрытия

Агент скажет «all tests pass», ни разу не запустив тесты. Это не злой умысел — модель обучена на данных, где фраза «all tests pass» встречается часто, и подгоняет паттерн. Даже если добавить инструмент запуска тестов, агент будет **выдумывать результат**, если промпт не сопротивляется. Контракт верификации — это набор правил в промпте, который заставляет агента запускать проверки и честно отчитываться.

---

## Проблема

Три уровня лжи (не злонамеренной, а статистической):

1. **Не запускал, но утверждает.** «All tests pass» — потому что так обычно заканчивается хороший отчёт в обучающих данных.
2. **Запускал не то.** Запустил один тест, а отчитался «все прошли».
3. **Запускал, но не знал как.** Проект использует `vitest`, а агент запустил `npm test` — и ничего не проверил, но отчитался об успехе.

Проблема глубже, чем «добавить инструмент». Нужен **контракт**: явное соглашение о том, что считается проверкой, в каком порядке её гонять и как честно отчитываться.

---

## Решение с кодом

### Обнаружение ворот из package.json scripts

Проверки у каждого проекта свои. Вместо того чтобы зашивать команды, агент **обнаруживает** их из `package.json`:

```typescript
import { readFileSync } from "node:fs";
import { join } from "node:path";

// Обнаруживаем доступные проверки из package.json scripts
function discoverGates(sandbox: Sandbox): string[] {
  const raw = sandbox.readFileSync
    ? readFileSync(join(sandbox.workingDirectory, "package.json"), "utf-8")
    : "";
  let scripts: Record<string, string> = {};
  try {
    scripts = JSON.parse(raw).scripts ?? {};
  } catch {
    return [];  // нет package.json → нет ворот
  }

  // Канонический порядок: typecheck → lint → test → build
  const order = ["typecheck", "lint", "test", "build"];
  return order.filter((gate) => gate in scripts);
}
```

Порядок **typecheck → lint → test → build** — не случаен:

| Шаг | Что ловит | Почему первым |
|---|---|---|
| `typecheck` | Ошибки типов | Самый дешёвый и быстрый, ловит грубые ошибки |
| `lint` | Стиль, анти-паттерны | Дёшево, до запуска тяжёлых тестов |
| `test` | Логика | Дороже, но проверяет поведение |
| `build` | Сборка целиком | Самый дорогой — только если всё остальное прошло |

Гонять проверки в этом порядке — значит падать **быстро и дёшево**: если типы не сходятся, нет смысла гонять сборку.

### Контракт верификации в промпте

```typescript
sections.push(`# Verification
After making changes, verify your work:
1. Run \`npx tsc --noEmit\` when TypeScript is present
2. Run lint, test, or build commands only if they exist in this project
   and are allowed by the current approval mode
3. Report exactly what you ran, what was blocked, and what was unavailable
4. Do NOT inflate partial verification into a blanket success claim

Do NOT claim "tests pass" without running them.
Scope your claims honestly. "Verification was limited because writes were blocked"
is honest. "All tests pass" when you didn't run them is not.`);
```

> **📝 Перевод промта (контракт Verification):**
>
> *«После внесения изменений проверь свою работу:*
> *1. Запусти `npx tsc --noEmit`, если проект использует TypeScript*
> *2. Запускай lint, тесты или сборку только если они существуют в этом проекте и разрешены текущим режимом одобрения*
> *3. Отчитывайся точно: что запускал, что было заблокировано, что недоступно*
> *4. Не раздувай частичную проверку в заявление о полном успехе*
>
> *Не утверждай «тесты прошли», не запуская их.*
> *Ограничивай свои заявления честно. «Проверка была ограничена, потому что запись была заблокирована» — честно. «Все тесты прошли», когда ты их не запускал — нет.»*

### Scoped claims — что агент может сказать vs что нужно

| Может сказать (конфабуляция) | Нужно (честный отчёт) |
|---|---|
| «All tests pass» | «Ran npm test: 47 passed, 3 failed (pre-existing, unrelated to my change)» |
| «I fixed the bug» | «Fixed null check in auth.ts:42. npx tsc --noEmit passes. Tests blocked by approval.» |
| «The build works» | «Ran npm run build: succeeded in 4.2s, no warnings.» |

Ключевое в scoped claims — **отделять свои изменения от предсуществующих проблем**. Формула: *«3 pre-existing failures, my change added none»* — это честно, потому что разграничивает «что уже было сломано» и «что сломал я».

### Маркер конфабуляции

Следи за мягкими фразами: **«should be fine»**, **«looks good to me»**, **«I expect this to work»**. Это маркеры. Модель, реально запустившая проверку, использует **прошедшее время и конкретный результат**. Не запустившая — уклончивое будущее время:

| Маркер конфабуляции | Маркер реальной проверки |
|---|---|
| «It should be fine» | «It ran: 47 passed, 3 failed» |
| «I expect this to work» | «Build succeeded in 4.2s» |
| «Looks good to me» | «npx tsc --noEmit: no errors» |

---

## Ключевые выводы

- **Агент врёт о проверках статистически** — не злонамеренно, а подгоняя паттерн «all tests pass». Нужен контракт в промпте, а не только инструмент.
- **Ворота обнаруживаются из `package.json` scripts** — не зашиваются. Порядок **typecheck → lint → test → build** даёт «падать быстро и дёшево».
- **Scoped claims:** отделяй свои изменения от предсуществующих проблем. «3 pre-existing failures, my change added none» — честно.
- **Маркер конфабуляции — будущее время:** «should be fine», «I expect this to work». Реальная проверка — прошедшее время и конкретные числа.
- **Честность ценнее покрытия.** «Проверка была ограничена, потому что запись заблокирована» — лучше, чем выдуманный «всё прошло».

## Попробуй сам

1. Дай агенту задачу, после которой он должен запустить тесты, но **заблокируй** `bash`. Посмотри, отчитается ли он честно «проверка заблокирована» или выдумает «всё прошло».
2. Добавь контракт верификации в промпт и повтори. Сравни формулировки отчёта.
3. Реализуй `discoverGates` и проверь на проекте с `package.json`: какие ворота обнаружатся, в каком порядке.
4. Проверь scoped claims: дай проекту с **предсуществующими** падающими тестами задачу «добавь X». Убедись, что агент отличает «уже падало» от «сломал я».
5. Собери список мягких фраз-маркеров («should be fine» и т.п.) и проверь, использует ли их агент, когда не запускал проверку.
