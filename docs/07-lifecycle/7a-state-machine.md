# Урок 7a: Машина состояний облачной песочницы

Облачная песочница — это не бинарное «работает» или «остановлена». Это **машина состояний**: ВМ проходит через несколько фаз, и в каждой — своя стоимость, свои таймеры и свои правила. Понять эти состояния — значит понять, почему жизненный цикл песочницы вообще нужен и как на нём экономить.

---

## Проблема

Наивная модель: «создал песочницу → поработал → закрыл». В ней нет ответов на реальные вопросы:

- Что происходит между «создал» и «можно работать»? (ВМ запускается, ставятся зависимости — это **время и деньги**.)
- Что делать, если пользователь ушёл на обед, а песочница продолжает тикать и **жечь деньги** поминутно?
- Как «поставить песочницу на паузу», не потеряв её состояние, чтобы вернуться к ней через час?

Без явной машины состояний все эти случаи обрабатываются кое-как: где-то ВМ живёт до жёсткого таймаута и сжигает бюджет, где-то закрывается слишком рано и теряет работу пользователя.

---

## Решение с кодом

Четыре состояния и два таймера.

### Четыре состояния

```
provisioning ──► active ──► hibernating ──► hibernated
                  ▲              │
                  └──────────────┘  (restore — восстановление)
```

```typescript
type SandboxState =
  | "provisioning"   // ВМ запускается, ставятся зависимости
  | "active"         // агент работает, команды выполняются
  | "hibernating"    // снимок в процессе, песочница завершает работу
  | "hibernated";    // ВМ остановлена, снимок сохранён
```

| Состояние | Что происходит | Стоимость |
|---|---|---|
| **Provisioning** | ВМ запускается, зависимости устанавливаются | Биллинг уже начался |
| **Active** | Агент работает, команды выполняются | Полная поминутная ставка |
| **Hibernating** | Снимок в процессе, песочница завершает работу | Полная ставка (короткий переход) |
| **Hibernated** | ВМ остановлена, снимок сохранён | **Только хранение** (дёшево) |

### Два таймера

Два независимых таймера управляют переходами. Первый — жёсткий срок, второй — окно неактивности:

```typescript
interface LifecycleConfig {
  // Жёсткий срок жизни: даже при постоянной активности песочница
  // не живёт дольше этого. Обычно 1–4 часа.
  hardLimitMs: number;          // например, 4 * 60 * 60 * 1000

  // Окно неактивности: если пользователь молчит дольше этого,
  // песочница уходит в гибернацию. Обычно 5 минут.
  inactivityWindowMs: number;   // например, 5 * 60 * 1000
}

function nextState(state: SandboxState, timers: {
  elapsedMs: number;            // сколько прошло с создания
  sinceLastActivityMs: number;  // сколько прошло с последней активности
}, config: LifecycleConfig): SandboxState {
  // Жёсткий срок: активность не спасает от завершения
  if (timers.elapsedMs >= config.hardLimitMs) {
    return "hibernating";
  }
  // Окно неактивности: пользователь молчит → на паузу
  if (timers.sinceLastActivityMs >= config.inactivityWindowMs) {
    return "hibernating";
  }
  return "active";
}
```

- **Жёсткий срок (1–4 часа):** потолок жизни песочницы. Даже если пользователь активен, через N часов ВМ обязана завершиться. Это защита от «забытой» песочницы, которая жжёт деньги бесконечно.
- **Окно неактивности (5 минут):** если пользователь ничего не делал 5 минут, песочница уходит в гибернацию. Именно этот таймер даёт основную экономию.

### Опрос НЕ считается активностью

Критичное правило. Lifecycle-workflow периодически опрашивает статус песочницы («жива ли?», «не пора ли гибернировать?»). Если бы каждый такой опрос считался активностью, окно неактивности **никогда бы не закрывалось** — опрос сам по себе держал бы песочницу «активной» вечно.

```typescript
type ActivitySource = "user" | "tool_call" | "file_change" | "poll";

// Трекер активности учитывает ТОЛЬКО пользовательские события.
// Опрос статуса (poll) сюда не входит.
function isUserActivity(source: ActivitySource): boolean {
  return source === "user" || source === "tool_call" || source === "file_change";
}
```

### Таймлайн-пример

Вот как выглядит жизнь песочницы с конфигурацией «жёсткий срок 4 часа, окно неактивности 5 минут»:

```
t=0       provisioning   ВМ создаётся, ставятся зависимости        $ стартует
t=40с     active         агент получает первую задачу               полная ставка
t=12:00   active         пользователь активно работает              полная ставка
t=12:05   active         пользователь ушёл, тишина                  полная ставка
t=12:10   hibernating    окно 5 мин истекло → снимок ФС             полная ставка
t=12:30   hibernated     ВМ остановлена, снимок сохранён            только хранение
─────────────────────────────────────────────────────────────────────────────
t=14:20   active         пользователь вернулся → restore из снимка  полная ставка
t=14:25   active         работа продолжается                        полная ставка
t=15:00   hibernating    снова тишина 5 мин → гибернация            полная ставка
t=16:00   hibernated     жёсткий срок мог бы наступить только в 4ч  только хранение
```

Обрати внимание: песочница была «живой» суммарно ~25 минут из 4 часов, но пользователь при этом вернулся и продолжил работу с того же места. Состояние не потерялось — оно было заморожено в снимок.

---

## Ключевые выводы

- **Четыре состояния, не два:** `provisioning → active → hibernating → hibernated`. ВМ не «включена/выключена», а проходит жизненный цикл.
- **Два таймера:** жёсткий срок (1–4 ч) — потолок жизни даже при активности; окно неактивности (5 мин) — основная экономия.
- **`hibernating` — переходное состояние:** снимок ещё пишется, ВМ ещё не остановлена, поэтому биллинг идёт по полной ставке.
- **Опрос НЕ считается активностью.** Иначе окно неактивности никогда не закроется — опрос сам держал бы песочницу «живой».
- **Экономия рождается из окна неактивности:** 25 минут полной ставки против 4 часов.

## Попробуй сам

1. Нарисуй диаграмму переходов и подпиши, **какое событие** вызывает каждый переход (истечение окна неактивности, истечение жёсткого срока, `restore` при возврате пользователя).
2. Реализуй `nextState` как чистую функцию и напиши юнит-тесты: активность в пределах окна → `active`; тишина сверх окна → `hibernating`; сверх жёсткого срока даже при активности → `hibernating`.
3. Добавь в трекер активности источник `poll` и посмотри, как изменится поведение: окно неактивности перестанет закрываться. Убери `poll` обратно.
4. Поэкспериментируй с параметрами: что будет при `inactivityWindowMs = 60с`? При `hardLimitMs = 30 мин`? Найди, где начинаются «петли» и лишние гибернации.
5. Замерь стоимость по таймлайну из урока (25 мин × ставку) и сравни с «без жизненного цикла» (4 ч × ставку).
