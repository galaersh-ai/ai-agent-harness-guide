# Урок 7c: Долговечные workflow — таймеры в serverless

Машина состояний из урока 7a требует таймеров: «через 5 минут неактивности — гибернировать», «через 4 часа — завершить». Но где эти таймеры живут? Если каркас работает в serverless-окружении (как у Vercel), обычный `setTimeout` там **не работает**. Этот урок — о том, как строить долговечные отложенные задачи в мире, где процесс может умереть в любой момент.

---

## Проблема

В serverless функция выполняется короткое время (секунды), а потом **замораживается или уничтожается**. Код вроде:

```typescript
// НАИВНО: этот таймер умрёт вместе с функцией
setTimeout(() => hibernateSandbox(id), 5 * 60 * 1000);
```

не переживёт завершения функции. Через 5 минут, когда таймер должен сработать, процесса уже нет — и гибернация не произойдёт. Песочница продолжит жечь деньги до жёсткого срока.

То же самое с «подождать 30 секунд и проверить, не появилась ли активность»: любой `sleep`, привязанный к жизни функции, — это иллюзия. Нужен механизм, который **переживает** завершение функции и возобновляет работу в новом процессе.

---

## Решение с кодом

Идея долговечного workflow: вместо «спать в памяти» — **чекпоинтить состояние в долговечное хранилище и планировать следующее пробуждение**.

### Vercel Workflow: sleep() чекпоинтит в долговечное хранилище

В Vercel Workflow функция `sleep()` — не обычный `setTimeout`. Она **сохраняет точку выполнения в долговечное хранилище** и завершает текущий процесс. Когда время истекает, workflow просыпается в **новом** процессе и продолжает с того же места:

```typescript
import { createWorkflow, sleep } from "@vercel/workflow";

export const sandboxLifecycle = createWorkflow({
  async run({ sandboxId }: { sandboxId: string }) {
    // Каждый sleep() — это чекпоинт: состояние сохраняется,
    // процесс завершается, через N секунд workflow просыпается заново.
    await sleep(30);                 // подождать 30 секунд (долговечно!)

    const sandbox = await fetchSandbox(sandboxId);
    const activity = await getLastActivity(sandboxId);

    if (isUserActivity(activity)) {
      // Пользователь был активен — планируем следующую проверку
      await sleep(30);
      // ... снова проверка
    } else if (await isIdleBeyondWindow(sandboxId)) {
      await hibernate(sandboxId);    // окно неактивности истекло → на паузу
    }
  },
});
```

Ключевая разница с `setTimeout`:

| | `setTimeout` | Workflow `sleep()` |
|---|---|---|
| Где живёт | В памяти процесса | В долговечном хранилище |
| Переживает завершение функции | ❌ Нет | ✅ Да |
| Стоимость простоя | Процесс висит и жжёт деньги | Процесс завершён, платишь только за чекпоинт |
| Ограничение по времени | Лимит времени функции | Часы/дни |

### Step-функции ретраятся

Аналог в других облаках — step-функции (AWS Step Functions, Temporal, и т.п.). Их ключевое свойство для нас: **каждый шаг ретраится**. Если шаг упал (сеть, сбой провайдера), он повторится автоматически, а не потеряется:

```typescript
// Концептуально: step-функция = цепочка шагов, каждый из которых
// долговечен и ретраится. Упавший шаг "проверить статус" повторится,
// а не тихо потеряется, как setTimeout.
const workflow = [
  step("wait-30s",     () => sleep(30)),           // ретраится
  step("check",        () => checkActivity(id)),   // ретраится
  step("maybe-hiber",  () => hibernate(id)),       // ретраится
];
```

Именно **ретраи** отличают долговечный workflow от хрупкого таймера: в serverless падения — норма, и каждый шаг должен уметь пережить их.

### Математика: зачем всё это нужно

| Сценарий | Время полной ставки | Стоимость (при $0.02/мин) |
|---|---|---|
| **Без жизненного цикла** — песочница живёт до жёсткого срока (4 ч) | 240 мин | **$4.80** |
| **С гибернизацией по неактивности (5 мин)** — песочница «жила» ~25 мин | 25 мин | **$0.50** |

Разница — **почти в 10 раз**. И достигается она именно долговечным таймером, который умеет «проснуться через 5 минут тишины» и отправить песочницу в гибернацию. Без долговечного workflow этот таймер просто не выжил бы в serverless.

> **Интуиция:** долговечный workflow — это не «долгий сон», а «записка самому себе в будущее». Ты записываешь состояние в хранилище, завершаешься, а планировщик будит тебя позже и отдаёт записку. Поэтому workflow может «ждать» часы, не занимая ни одного процесса.

---

## Ключевые выводы

- **`setTimeout` не работает в serverless.** Функция завершается, и таймер умирает вместе с ней.
- **Workflow `sleep()` чекпоинтит в долговечное хранилище:** состояние сохраняется, процесс завершается, через N секунд workflow просыпается в новом процессе.
- **Step-функции ретраятся:** упавший шаг повторяется, а не теряется. В serverless падения — норма.
- **Математика:** без жизненного цикла — $4.80 за сессию, с гибернизацией по неактивности — $0.50. Почти 10-кратная экономия.
- **Ментальная модель:** долговечный workflow — это «записка в будущее», а не «долгий сон». Никакого висящего процесса.

## Попробуй сам

1. Напиши наивный `setTimeout(() => hibernate(id), 5 * 60_000)` в serverless-функции и понаблюдай: при завершении функции таймер исчезнет. Зафиксируй, что гибернация не произошла.
2. Перепиши тот же сценарий через workflow `sleep(30)` и проверь, что после «сна» состояние продолжает выполняться — уже в новом процессе.
3. Реализуй простой долговечный workflow локально: сохраняй состояние в файл/БД, завершайся, а по внешнему триггеру — читай состояние и продолжай. Это прототип чекпоинта.
4. Добавь ретраи: намеренно урони шаг «проверить статус» и убедись, что он повторился, а не потерялся.
5. Посчитай стоимость для своего сценария: поменяй ставку, окно неактивности и жёсткий срок — и посмотри, как меняется итоговая цифра.
