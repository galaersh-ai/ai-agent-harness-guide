# Урок 4d: Облачная песочница

Локальная песочница быстрая, но без изоляции. `just-bash` изолирует файловую систему, но не даёт настоящего окружения (реальные `git`, `npm`, сеть). Третья реализация интерфейса `Sandbox` — **облачная песочница**: отдельная виртуальная машина, где команды выполняются по-настоящему, изолированно от твоей машины. Это концептуальный урок: конкретный API зависит от провайдера (Vercel Sandbox, E2B, Firecracker), но форма и компромиссы — общие.

## Проблема

Что не умеют две предыдущие реализации:

| Реализация | Чего не хватает |
|------------|-----------------|
| Local | Нет изоляции — `rm -rf` выполнится по-настоящему |
| just-bash | ФС виртуальна, но `git`/`npm` симулированы, сети и настоящих процессов нет |

Облачная песочница закрывает оба пробела: это **полноценная ВМ** с настоящей файловой системой, настоящим `git`, настоящим `npm`, сетью и процессами. Но за это платишь двумя вещами:

1. **Все операции — сетевые вызовы.** Чтение файла — это запрос к API провайдера, а не локальный вызов.
2. **Поминутная оплата.** ВМ живёт ограниченное время и стоит денег, пока активна.

## Решение с кодом

Форма реализации (концептуально — реальный API зависит от провайдера):

```typescript
async function createCloudSandbox(config): Promise<Sandbox> {
  const vm = await VercelSandbox.create(config);

  return {
    type: "cloud",
    workingDirectory: "/workspace",

    expiresAt: Date.now() + 30 * 60 * 1000,  // 30 минут

    readFile: async (p) => vm.files.read(resolve("/workspace", p)),

    exec: async (command) => {
      const result = await vm.commands.run(command, { cwd: "/workspace" });
      return { stdout: result.stdout + result.stderr, exitCode: result.exitCode };
    },

    stop: async () => vm.close(),

    snapshot: async () => {
      const snap = await vm.snapshot();
      return { snapshotId: snap.id };
    },
  };
}
```

### Ключевые отличия от локальной реализации

1. **`readFile` и `exec` — сетевые вызовы.** `vm.files.read(...)` и `vm.commands.run(...)` уходят на API провайдера. Каждый вызов — это задержка в десятки–сотни миллисекунд (а не микросекунды, как у локальной).

2. **`expiresAt` появляется.** У облачной ВМ есть срок жизни — здесь `30 минут`. По истечении ВМ останавливается (или переходит в гибернацию — об этом в уроке 4e). Это то самое опциональное поле из интерфейса `Sandbox`.

3. **`snapshot()` появляется.** Можно сделать снимок состояния ВМ и потом восстановиться из него. У локальной ФС и у `just-bash` такого смысла нет.

4. **`stop()` по-настоящему освобождает ресурсы** — `vm.close()` завершает ВМ и **останавливает биллинг**. Это не пустая функция, как у локальной.

### `expiresAt` и `snapshot` опциональны — это важно

Интерфейс `Sandbox` объявляет их как `expiresAt?` и `snapshot?()`. Облачная реализация их **предоставляет**, локальная и just-bash — **нет**. Потребитель обязан проверять наличие:

```typescript
if (sandbox.expiresAt && Date.now() > sandbox.expiresAt) {
  // ВМ истекла — нужно восстановить или пересоздать
}

if (sandbox.snapshot) {
  const { snapshotId } = await sandbox.snapshot();
}
```

Это честный контракт: код не предполагает, что у любой песочницы есть срок жизни или снимки. Возможности, которых нет, просто отсутствуют в типе.

## Таблица компромиссов

Три реализации — три разных компромисса. Выбирай по задаче:

| | Local | just-bash | Cloud |
|---|---|---|---|
| **Стоимость** | Бесплатно | Бесплатно | Поминутно |
| **Задержка** | Микросекунды | Микросекунды | Десятки–сотни мс |
| **Изоляция** | Нет | Частичная (CoW) | Полная, отдельная ВМ |
| **git, npm** | Локальная установка | Симулированы | Реальные |
| **Персистентность** | Всё сохраняется | Изменения теряются | Снимки/гибернация |
| **Таймаут** | Нет | Нет | Жёсткий лимит 30–60 мин |

Как читать таблицу:

- **Local** — быстрее всего, но опаснее всего. Подходит для доверенных задач на своей машине.
- **just-bash** — безопасная середина для чтения и экспериментов, когда не нужны настоящие `git`/`npm`.
- **Cloud** — единственный вариант для настоящей изоляции и полноценного окружения, но платишь деньгами и задержкой.

Универсального «лучшего» варианта нет — есть правильный выбор под конкретную задачу. Именно поэтому интерфейс `Sandbox` единый: каркас не должен меняться от того, какой бэкенд выбран.

## Ключевые выводы

- **Облачная песочница = сетевые вызовы**: каждый `readFile`/`exec` уходит на API провайдера, отсюда задержка в десятки–сотни мс.
- **`expiresAt` и `snapshot()` — опциональны** в интерфейсе, их предоставляет только облачная реализация; потребитель проверяет наличие.
- **`stop()` = `vm.close()`** — освобождает ВМ и останавливает биллинг, в отличие от пустой функции локальной реализации.
- **Три компромисса** (стоимость, задержка, изоляция, персистентность, таймаут) — таблица, по которой выбирают бэкенд под задачу.
- **Единый интерфейс** позволяет каркасу не знать, какой бэкенд выбран.

## Попробуй сам

1. Напиши заглушку `createCloudSandbox` с фейковым `vm`-объектом (просто возвращающим строки) и проверь, что инструменты работают с ней без изменений.
2. Реализуй проверку `expiresAt`: если время истекло, логируй «песочница истекла» и не давай выполнять команды.
3. Добавь в `createCloudSandbox` логику: перед `exec` проверять `Date.now() > expiresAt` и бросать осмысленную ошибку.
4. Сравни на глаз таблицу компромиссов и реши, какой бэкенд ты бы выбрал для: (а) локального рефакторинга, (б) запуска чужих PR-тестов в CI, (в) обучения агента работе с настоящим `git`.
