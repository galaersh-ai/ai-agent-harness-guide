# Урок 8b: Конфигурация одобрения — два уровня защиты

Кто решает, можно ли агенту выполнить опасную команду — человек или политика? И **какие** команды вообще опасны? Это два разных вопроса, и ответы на них живут на **двух разных уровнях**. Урок 8b — о том, как развести «кто решает» и «какие политики» по разным механизмам, а затем объединить их в оборону в глубину.

---

## Проблема

Один механизм (например, только `needsApproval: true`) не различает ситуации: локальному пользователю нужно спрашивать, CI-пайплайну — авто-одобрять, а субагенту — доверять лишь малую часть команд. А отдельно от «кто решает» стоит вопрос «какие политики действуют всегда»: например, запись в `.env` запрещена **при любом** режиме, независимо от того, кто решает.

Если свалить оба вопроса в одну кучу, получится неконфигурируемая каша: правило, зашитое в один `if`, нельзя ни переопределить для CI, ни защитить от обхода.

---

## Решение с кодом

Два уровня: **config** (кто решает) и **events** (какие политики).

### Уровень 1 — config: кто решает

Это discriminated union из урока 6c, но теперь осознанно оформленный как **конфигурация одобрения**:

```typescript
type ApprovalConfig =
  | { mode: "interactive" }                    // человек решает
  | { mode: "background" }                     // авто-одобрение (CI)
  | { mode: "delegated"; trust: string[] };    // субагент с ограниченным доверием

function createApproval(config: ApprovalConfig) {
  return ({ command }: { command: string }) => {
    if (config.mode === "background") return false;      // всё разрешено
    if (config.mode === "delegated") {
      return !config.trust.some((p) => command.trim().startsWith(p));
    }
    // interactive: безопасные — автоматически, остальное — спросить человека
    return !SAFE_PREFIXES.some((p) => command.trim().startsWith(p));
  };
}
```

Три режима на месте вызова:

```typescript
// Локальная разработка: человек одобряет опасные команды
const bash = createBashTool(localOps, createApproval({ mode: "interactive" }));

// CI/автоматизация: всё выполняется автоматически
const bash = createBashTool(localOps, createApproval({ mode: "background" }));

// Субагент: наследует только часть доверия от родителя
const bash = createBashTool(localOps, createApproval({
  mode: "delegated",
  trust: ["npm test", "npm run build", "npx tsc"],
}));
```

**Config отвечает на вопрос «кто решает»:** человек (interactive), никто (background — всё можно), или доверенный список (delegated).

### Уровень 2 — events: какие политики

Поверх config работает событийная шина (см. урок 11c). Подписка на `tool_call` позволяет задать политики, которые действуют **независимо** от режима:

```typescript
// Политика, которая действует ПРИ ЛЮБОМ режиме одобрения
const PROTECTED = [".env", "package-lock.json"];

harness.on("tool_call", async ({ toolName, input }) => {
  if (toolName === "write" && PROTECTED.some((p) => input.path.endsWith(p))) {
    return { block: true, reason: `${input.path} is protected by policy.` };
  }
});
```

Здесь нет выбора «кто решает» — политика безусловна. Даже `background` (CI) не сможет записать в `.env`, потому что policy-слой блокирует запись раньше, чем срабатывает одобрение.

### Комбинирование = оборона в глубину

Два уровня работают **последовательно**, а не «или-или»:

```
Вызов команды
    │
    ▼
[Уровень 2: events] ── политики (запрещено ВСЕГДА?) ──► block? → стоп
    │  нет блокировки
    ▼
[Уровень 1: config] ── кто решает? ──► interactive/delegated/background
    │
    ▼
Выполнение
```

| Уровень | Механизм | Отвечает на вопрос | Пример |
|---|---|---|---|
| Config | `createApproval(config)` | **Кто** решает | interactive / background / delegated |
| Events | `harness.on("tool_call")` | **Какие** политики всегда действуют | запрет записи в `.env` |

Почему это «оборона в глубину», а не дублирование:

- **Config** — это намерение контекста: «здесь человек», «здесь CI», «здесь субагент». Он **меняется** от вызова к вызову.
- **Events** — это инварианты системы: «запись в `.env` запрещена всегда». Они **не меняются** и не зависят от контекста.
- Вместе они дают: гибкость (config) + гарантию (events). Ни один слой сам по себе не даёт обоих свойств.

### Полный пример: соединение уровней

```typescript
function createProtectedBash(sandbox, config: ApprovalConfig, bus: EventBus) {
  const approval = createApproval(config);   // уровень 1: кто решает
  const bash = createBashTool(sandbox, approval);

  // уровень 2: какие политики (действуют всегда, поверх одобрения)
  bus.on("tool_call", async ({ toolName, input }) => {
    if (toolName === "write" && PROTECTED.some((p) => input.path.endsWith(p))) {
      return { block: true, reason: `${input.path} is protected by policy.` };
    }
  });

  return bash;
}
```

---

## Ключевые выводы

- **Два вопроса — два уровня:** «кто решает» (config) и «какие политики» (events). Не смешивай их в одном `if`.
- **Config — кто решает:** `interactive` (человек), `background` (CI, всё можно), `delegated` (субагент, доверенный список).
- **Events — какие политики:** подписки на `tool_call` задают инварианты, действующие при любом режиме (например, запрет `.env`).
- **Комбинирование = оборона в глубину:** сначала политики (независимые инварианты), потом одобрение (контекстное решение). Ни один слой в одиночку не даёт и гибкости, и гарантии.
- **Config — это данные, а не код:** его можно грузить из файла, валидировать через Zod, сериализовать и менять без правки каркаса.

## Попробуй сам

1. Запусти `bash` в режиме `interactive` и дай опасную команду (`rm -rf /`) — убедись, что она запросит одобрение, а безопасная (`npm test`) — пройдёт автоматически.
2. Переключи в `background` и повтори: обе команды пройдут без спроса. Это режим CI.
3. Добавь политику «запрет записи в `.env`» через `harness.on("tool_call")` и убедись, что запись блокируется **даже** в режиме `background`.
4. Проверь режим `delegated` с trust-листом: `npm test` проходит, `npm install` — блокируется.
5. Соедини оба уровня в `createProtectedBash` и проверь порядок: политика должна срабатывать раньше одобрения.
