# Урок 6c: Executor — исполнитель с ограниченным доверием

Executor — второй тип субагента. Если Explorer **исследует**, то Executor **делает**: пишет код, правит файлы, запускает тесты и сборку. Он получает больше возможностей, чем Explorer, — но ровно столько, сколько нужно для исполнения, и ни каплей больше. Вся сложность Executor-а — в том, **как** ограничить его возможности, не парализовав.

---

## Проблема

Исполнение требует записи: править файлы, запускать `npm test`, гонять сборку. Но дать Executor-у полный `bash` — значит вернуть режим отказа №3 из урока 6a: агент с широкими возможностями рано или поздно сделает что-то лишнее. `npm install какой-то-случайный-пакет`, `rm -rf`, произвольные команды — всё это не должно быть доступно исполнителю, которому поручили «поправить функцию и прогнать тесты».

При этом Executor должен быть **сильнее** Explorer-а: он пишет код, а значит, ему нужна модель, способная рассуждать о корректности изменений.

---

## Решение с кодом

Executor = `read` + `grep` + `bash(delegated)` + Sonnet + 15 шагов.

```typescript
import { ToolLoopAgent, stepCountIs } from "ai";

function buildExecutor(sandbox, parentTools) {
  // bash с делегированным доверием — см. урок 8b про approval-конфиг
  const executorBash = createBashTool(sandbox, createApproval({
    mode: "delegated",
    trust: ["npm test", "npm run build", "npx tsc"],
  }));

  return new ToolLoopAgent({
    model: "anthropic/claude-sonnet-4-6",      // более сильная модель
    instructions: `You are an executor agent. Follow instructions precisely.
    Working directory: ${sandbox.workingDirectory}
    Do NOT ask questions. Do NOT explore beyond what's needed. Execute the task.`,
    tools: {
      read: parentTools.read,
      grep: parentTools.grep,
      bash: executorBash,
    },
    stopWhen: stepCountIs(15),                 // лимит 15 шагов
  });
}
```

> **📝 Перевод промта (Executor):**
>
> *«Ты — агент-исполнитель. Следуй инструкциям точно. Рабочая директория: …*
> *Не задавай вопросов. Не исследуй сверх необходимого. Выполни задачу.»*
>
> *Три директивы — это весь характер Executor-а: точность («следуй точно»), автономность («не задавай вопросов»), сдержанность («не исследуй сверх нужного»). Он не планирует, не уточняет, не размышляет об архитектуре — он выполняет.*

### Trust list намеренно мал

Самая важная строка — `trust: ["npm test", "npm run build", "npx tsc"]`. Это **весь** список команд, которые Executor может запускать без спроса:

```typescript
function createApproval(config: ApprovalConfig) {
  return ({ command }: { command: string }) => {
    if (config.mode === "background") return false;      // всё разрешено
    if (config.mode === "delegated") {
      // Команда разрешена, только если начинается с одного из доверенных префиксов
      return !config.trust.some((p) => command.trim().startsWith(p));
    }
    // interactive: безопасные — автоматически, остальное — спросить человека
    return !SAFE_PREFIXES.some((p) => command.trim().startsWith(p));
  };
}
```

> **📝 Комментарий переводчика:**
>
> *Режим `delegated` со списком `trust: ["npm test", "npm run build", "npx tsc"]` означает: субагент может запускать тесты, сборку и проверку типов, но не может устанавливать пакеты, не может модифицировать файлы напрямую через произвольные команды, не может выполнять ничего другого. Список доверия намеренно мал.*

Три команды — это **замкнутый цикл верификации**: проверка типов (`npx tsc`) → тесты (`npm test`) → сборка (`npm run build`). Этого достаточно, чтобы Executor мог проверить свою работу, но недостаточно, чтобы навредить. `npm install` сюда сознательно не входит — установка зависимостей требует решения родителя или человека.

### Качество инструкций критично

Executor не задаёт вопросов и не уточняет. Это значит: **всё, что ему нужно знать, должно быть в переданной задаче**. Если родитель скажет «поправь баг в авторизации», Executor будет гадать, где именно баг и как чинить. Если родитель скажет «в `src/auth.ts:42` замени `if (user)` на `if (user?.id)`, затем прогони `npm test`» — Executor сделает ровно это.

Плохая инструкция → Executor гадает (и ошибается). Хорошая инструкция → Executor выполняет точно. Родитель, который умеет формулировать задачи, — половина успеха делегирования:

```
Плохо:  "Fix the auth bug"
Хорошо: "In src/auth.ts, the null check at line 42 is missing an optional
         chaining. Change `if (user)` to `if (user?.id)`. Then run `npm test`
         and report the result."
```

### Сравнение Explorer vs Executor

| Параметр | Explorer | Executor |
|---|---|---|
| Инструменты | `read`, `grep` | `read`, `grep`, `bash` (delegated) |
| Модель | `claude-haiku-4-5` (быстрая) | `claude-sonnet-4-6` (сильная) |
| Бюджет шагов | 5 | 15 |
| Может модифицировать | **Нет** | Да (в пределах trust-листа) |
| Может спрашивать пользователя | **Нет** | **Нет** |
| Назначение | Понять и доложить | Сделать и проверить |
| Стоимость | Минимальная | Средняя |

## Ключевые выводы

- **Executor = `read` + `grep` + `bash(delegated)` + Sonnet + 15 шагов.** Больше возможностей, чем у Explorer-а, но строго ограниченных.
- **Trust list намеренно мал:** три команды (`npm test`, `npm run build`, `npx tsc`) — замкнутый цикл верификации, достаточный для проверки, недостаточный для вреда.
- **Качество инструкций критично:** Executor не уточняет и не спрашивает, поэтому всё нужное должно быть в задаче. Родитель обязан формулировать точно.
- **Модель сильнее, чем у Explorer-а:** написание кода требует рассуждений, которых у Haiku не хватает.
- **Лимит шагов выше (15):** исполнение — это цикл «изменил → проверил → поправил», ему нужно больше места, чем исследованию.

## Попробуй сам

1. Дай Executor-у команду `npm install lodash` и посмотри, что он получит в ответ. Он должен вернуть строку блокировки (`Blocked: ... requires approval.`), а не выполнить команду.
2. Сформулируй задачу двумя способами — «поправь баг в авторизации» и «в `src/auth.ts:42` измени X на Y, прогони `npm test`». Сравни результаты: вторая выполнится точно, первая — с догадками.
3. Добавь в trust-лист `npm install` и посмотри, как быстро Executor начнёт ставить пакеты по своей инициативе. Верни список обратно и зафиксируй разницу.
4. Проверь поведение на лимите: дай задачу, требующую 20+ шагов, и увидишь, как `stepCountIs(15)` обрезает работу на середине. Это сигнал разбить задачу на две.
5. Сравни Explorer и Executor на **одной** задаче (например, «опиши структуру тестов в проекте»). Executor справится, но потратит больше денег — на исследование всегда бери Explorer.
