# Урок 5: Выполнение shell с безопасностью — паттерн фабрика

> Разбор курса «[Build Your Own AI Coding Agent Harness](https://vercel.com/academy/build-ai-agent-harness)» от Vercel Academy (автор — Joel Hooks). Перевод и адаптация на русский.

## Что узнаем в этом уроке

В уроке 3 мы написали инструмент `bash`, который выполняет команды через `execSync` прямо на локальной машине. Это работает — но зашито намертво. Как только появляется облачная песочница (или in-memory файловая система), нам приходится переписывать инструмент целиком.

В этом уроке мы применим **паттерн фабрика**, чтобы отделить «что видит модель» от «где реально выполняется команда». Мы научимся:
- выделять интерфейс `BashOperations` с единственным методом `exec()`;
- строить фабрику `createBashTool(operations, safePrefixes)`;
- понимать концепцию **шва** (seam) — границы между слоями;
- менять бэкенд выполнения (локальный → песочница) **одной строкой**.

---

## Проблема — что не работает и почему

### Инструмент, который знает слишком много

Вот как выглядел `bash` в уроке 3 — одним монолитным куском:

```typescript
const bash = tool({
  description: `...`,
  inputSchema: z.object({ command: z.string() }),
  execute: async ({ command }) => {
    if (!isSafe(command)) return `Blocked: ...`;
    const stdout = execSync(command, { cwd: process.cwd(), encoding: "utf-8" });
    return stdout;
  },
});
```

Всё в одном замыкании: описание, схема, проверка безопасности и — самое главное — **способ выполнения** (`execSync`). Это работает ровно до тех пор, пока команды выполняются на локальной машине через Node.js.

Проблема вскрывается, когда появляется второй способ выполнения:

- **Облачная песочница** (например, Vercel Sandbox) выполняет команды на удалённой ВМ через сетевой вызов — это `async`, это другой API, это другая модель ошибок.
- **In-memory файловая система** (just-bash) выполняет команды в виртуальной ФС с copy-on-write.

Если способ выполнения «зашит» в инструмент, то для каждой среды нужен **свой** `bash`, `read` и `grep` — с дублированием описаний, схем и проверок. Три среды × три инструмента = девять почти одинаковых реализаций, которые начнут расходиться.

### Анти-паттерн: copy-paste с правками

Соблазн прост: скопировать инструмент и поменять `execSync` на `sandbox.exec`. Но это ведёт к расхождению:

- описание `bash` для песочницы забудет секцию `WHEN NOT TO USE`;
- проверка безопасности в одном месте будет обновлена, в другом — нет;
- схема входа разъедется: в одном месте добавили параметр, в другом — забыли.

Каждое такое расхождение — незаметный баг. Модель видит **разные** инструменты в разных средах, хотя по смыслу это один и тот же инструмент.

---

## Решение — подход с полным кодом

### Идея: интерфейс + фабрика

Разделяем инструмент на два слоя:

1. **Верхний слой** — то, что видит модель: описание, схема, проверка безопасности. Он **не меняется** от среды к среде.
2. **Нижний слой** — то, что реально выполняет команду: `exec()`. Он **меняется** в зависимости от среды.

Между ними — **шов** (seam): интерфейс, по которому слои общаются. Всё, что видит модель, — *выше* шва. Всё, что выполняет команды, — *ниже* шва.

### Интерфейс BashOperations

```typescript
interface BashOperations {
  exec(command: string): Promise<{ stdout: string; exitCode: number }>;
}
```

Один метод `exec`, принимающий команду-строку и возвращающий Promise с выводом и кодом завершения. Заметь: метод **асинхронный** (`Promise`), даже если под капотом реализация синхронная. Это сознательное решение: облачный бэкенд реально async, и лучше иметь единую async-сигнатуру у всех реализаций, чем несовместимые.

### Фабрика createBashTool

Фабрика принимает реализацию `operations` и список `safePrefixes`, а возвращает готовый инструмент. Сама фабрика **не знает**, где будут выполняться команды, — ей это и не нужно.

```typescript
import { tool } from "ai";
import { z } from "zod";

function createBashTool(
  operations: BashOperations,
  safePrefixes: string[]
) {
  function isSafe(command: string): boolean {
    const trimmed = command.trim();
    return safePrefixes.some((prefix) => trimmed.startsWith(prefix));
  }

  return tool({
    description: `Execute a shell command in the working directory.

WHEN TO USE: running build commands, installing packages, running tests,
  git operations, directory listings.

WHEN NOT TO USE: reading file contents (use read instead).
  Searching for patterns (use grep instead).

DO NOT USE FOR: reading files (use read), searching code (use grep).

Only commands starting with an approved prefix are allowed.`,
    inputSchema: z.object({
      command: z.string().describe("Shell command to execute"),
    }),
    execute: async ({ command }) => {
      if (!isSafe(command)) {
        return `Blocked: "${command}" requires approval. Allowed prefixes: ${safePrefixes.join(", ")}`;
      }
      const { stdout, exitCode } = await operations.exec(command);
      if (exitCode !== 0) {
        return stdout || `(command exited with code ${exitCode})`;
      }
      return stdout || "(no output)";
    },
  });
}
```

> **📝 Перевод промта** (поле `description`):
>
> *«Выполни shell-команду в рабочей директории.*
>
> *КОГДА ИСПОЛЬЗОВАТЬ: запуск сборки, установка пакетов, запуск тестов, git-операции, просмотр списка файлов в директории.*
>
> *КОГДА НЕ ИСПОЛЬЗОВАТЬ: чтение содержимого файлов (используй read вместо этого). Поиск паттернов (используй grep вместо этого).*
>
> *НЕ ИСПОЛЬЗОВАТЬ ДЛЯ: чтения файлов (используй read), поиска по коду (используй grep).*
>
> *Разрешены только команды, начинающиеся с одобренного префикса.»*

Обрати внимание на новую деталь — обработку `exitCode`:

```typescript
const { stdout, exitCode } = await operations.exec(command);
if (exitCode !== 0) {
  return stdout || `(command exited with code ${exitCode})`;
}
return stdout || "(no output)";
```

Теперь инструмент честно сообщает модели, если команда завершилась с ошибкой. Модель видит `exitCode !== 0` и **не выдумывает** успех — это продолжение принципа «инструмент никогда не молчит» из урока 3. А строка `(no output)` закрывает случай, когда команда успешна, но ничего не напечатала (например, `pwd` в некоторых обёртках).

### Локальный бэкенд

Теперь — реализация для локальной машины. Это единственное место, где встречается `execSync`.

```typescript
import { execSync } from "node:child_process";

const SAFE_PREFIXES = [
  "ls",
  "cat",
  "pwd",
  "git status",
  "git log",
  "git diff",
];

const localOps: BashOperations = {
  exec: async (command) => {
    try {
      const stdout = execSync(command, {
        cwd: process.cwd(),
        encoding: "utf-8",
        timeout: 30_000,
      });
      return { stdout, exitCode: 0 };
    } catch (e: any) {
      return {
        stdout: e.stdout || e.stderr || e.message || "",
        exitCode: e.status ?? 1,
      };
    }
  },
};

const bash = createBashTool(localOps, SAFE_PREFIXES);
```

Разберём `localOps`:

- **`exec` оборачивает `execSync` в Promise.** Хотя внутри всё синхронно, наружу торчит async-интерфейс — единый для всех бэкендов.
- **`timeout: 30_000`** — страховка от зависших команд. Команда, которая висит дольше 30 секунд, убивается, а не вешает агента.
- **Обработка ошибок.** `execSync` бросает исключение при ненулевом коде выхода. Мы ловим его и *нормализуем* в `{ stdout, exitCode }`: вывод берём из `e.stdout`/`e.stderr`/`e.message`, код — из `e.status` (или `1`, если его нет). Важно: **не перебрасываем** исключение, а превращаем его в обычный результат — чтобы инструмент всегда возвращал строку, а не падал.

### Замена на песочницу — одна строка

Теперь главный фокус урока. Появляется облачная песочница с методом `exec`. Меняем **только** реализацию бэкенда:

```typescript
const sandboxOps: BashOperations = {
  exec: (command) => sandbox.exec(command),
};

const bash = createBashTool(sandboxOps, SAFE_PREFIXES);
```

Всё. Одна строка. Описание, схема, проверка безопасности, обработка `exitCode` — **не изменились**. Модель видит ровно тот же инструмент, что и раньше. Под капотом сменилась только «сантехника»: команды теперь уходят в песочницу, а не на локальную машину.

Вот где окупается шов. Вместо девяти расходящихся копий инструментов у нас:

- одна фабрика `createBashTool`;
- три реализации `BashOperations` (local, just-bash, cloud);
- три строчки сборки.

Аналогично строятся `read` и `grep` — через свои фабрики и тот же принцип внедрения бэкенда.

### Шов: что выше, а что ниже

Зафиксируем границу явно:

```
┌─────────────────────────────────────────────┐
│  ВЫШЕ ШВА (видит модель, не меняется)        │
│  • description — 5-секционный контракт        │
│  • inputSchema — Zod-схема                    │
│  • isSafe() — проверка по allowlist           │
│  • обработка exitCode, усечение вывода        │
├─────────────────────────────────────────────┤
│  ШОВ: interface BashOperations               │
│        exec(command) → { stdout, exitCode }  │
├─────────────────────────────────────────────┤
│  НИЖЕ ШВА (выполняет, меняется по среде)      │
│  • localOps    → execSync                    │
│  • justBashOps → jb.runCommand               │
│  • sandboxOps  → sandbox.exec                │
└─────────────────────────────────────────────┘
```

Правило простое: **если модель это «видит» (описание, схема) или это «правила» (безопасность) — оно выше шва и не зависит от среды. Если это «механика» выполнения — оно ниже шва и подменяется реализацией.**

### Собираем агента с фабрикой

Полная сборка для локальной разработки:

```typescript
const bash = createBashTool(localOps, SAFE_PREFIXES);

const agent = new ToolLoopAgent({
  model: "anthropic/claude-haiku-4-5",
  instructions: `You are a coding agent. Use your tools to act, not to describe.`,
  tools: { read, grep, bash },
  stopWhen: stepCountIs(10),
});
```

А чтобы переключиться на песочницу — меняем ровно одну строку (`localOps` → `sandboxOps`), и всё остальное остаётся нетронутым. Переключатель можно вынести в переменную окружения:

```typescript
const ops: BashOperations =
  process.env.SANDBOX === "cloud" ? sandboxOps : localOps;

const bash = createBashTool(ops, SAFE_PREFIXES);
```

## Ключевые выводы

- **Монолит «знает слишком много».** Когда способ выполнения зашит в инструмент, каждая новая среда требует переписывания — и ведёт к расхождению копий.
- **Фабрика разделяет два слоя.** `createBashTool(operations, safePrefixes)` строит инструмент, не зная, *где* выполняются команды.
- **Шов — это интерфейс.** `BashOperations.exec()` — единственная точка контакта между «что видит модель» и «что выполняется».
- **Всё выше шва — стабильно.** Описание, схема, безопасность не меняются при смене среды. Модель видит один и тот же инструмент всегда.
- **Всё ниже шва — подменяемо.** `execSync` → `sandbox.exec` — замена одной строкой, без правки логики инструмента.
- **Единая async-сигнатура.** Даже синхронная локальная реализация оборачивается в `Promise`, чтобы все бэкенды были взаимозаменяемы.
- **Нормализуй ошибки.** Бэкенд превращает исключения в `{ stdout, exitCode }`, а инструмент всегда возвращает строку — никогда не молчит и не падает.

## Попробуй сам

1. **Рефактори текущий bash.** Возьми монолитный `bash` из урока 3 и разбей его на `BashOperations` + `createBashTool`. Убедись, что поведение не изменилось.

2. **Напиши второй бэкенд.** Создай `mockOps`, который не выполняет команды, а возвращает фиксированный вывод (например, `"echoed: <command>"`). Подключи его через фабрику — и проверь, что агент работает с ним так же, как с локальным.

3. **Проверь шов.** Добавь в `localOps` таймаут и обработку ошибок. Убедись, что `sandboxOps` и `mockOps` не требуют повторения этой логики — она осталась выше шва, в фабрике.

4. **Симулируй ошибку.** Заставь `mockOps` возвращать `exitCode: 1` и `stdout: "test failed"`. Проверь, что модель честно сообщает о провале, а не выдумывает успех.

5. **Добавь переключатель.** Вынеси выбор бэкенда в переменную окружения (`SANDBOX`). Запусти агента с `SANDBOX=cloud` и без неё — убедись, что меняется только строка выбора бэкенда.
