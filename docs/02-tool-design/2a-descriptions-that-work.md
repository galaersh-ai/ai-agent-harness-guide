# Урок 4: Описания, которые работают — пять секций контракта

> Разбор курса «[Build Your Own AI Coding Agent Harness](https://vercel.com/academy/build-ai-agent-harness)» от Vercel Academy (автор — Joel Hooks). Перевод и адаптация на русский.

## Что узнаем в этом уроке

В уроке 2 мы ввели 4-секционный контракт описания инструмента. Теперь мы доведём его до полной формы — **5 секций**, добавив `USAGE`. А главное — поймём, *почему* это работает: описания — это единственный «интерфейс», через который модель узнаёт о наших инструментах, и от их качества зависит весь выбор инструментов.

Мы разберём:
- зачем нужна пятая секция `USAGE` — ограничения, которых не видно из схемы;
- как `EXAMPLES` заставляют модель повторять правильный формат вызова;
- почему описание инструмента — это **API для модели**, а не комментарий для людей;
- как токены описаний **кешируются** между ходами — и что это значит для стоимости;
- полную таблицу «зачем каждая секция».

---

## Проблема — что не работает и почему

### Описание — единственный канал связи с моделью

Модель не читает наш код. Она не видит реализацию `execute`, не знает про `MAX_GREP_MATCHES`, не догадывается о лимитах и ограничениях. Всё, что модель знает об инструменте, — это два поля: `description` (текст) и `inputSchema` (схема параметров). **Описание — это API для модели**, а мы — разработчики этого API.

Если описание слабое, модель принимает решения вслепую. Она не может «заглянуть внутрь» и увидеть, что `grep` обрезает вывод до 50 совпадений, а `read` — до 500 строк. Эти факты нужно **сообщить словами**, иначе модель будет удивляться поведению инструмента и совершать ошибки.

### Чего не хватает 4 секциям

Секции `WHEN TO USE`, `WHEN NOT TO USE`, `DO NOT USE FOR` и `EXAMPLES` отвечают на вопрос «**когда** использовать инструмент». Но есть ещё вопрос «**как** использовать» — и на него они не отвечают:

- что произойдёт, если вывод окажется слишком большим (лимиты)?
- какие значения параметров допустимы, а какие приведут к ошибке?
- есть ли ограничения, которых не видно из схемы?

Без этой информации модель делает наивные вызовы: ищет слишком общий паттерн, ожидает полный вывод, передаёт недопустимые значения. Отсюда — пятая секция `USAGE`.

---

## Решение — подход с полным кодом

### Пять секций контракта

Полная форма описания выглядит так:

```typescript
const grep = tool({
  description: `Search file contents using regex. Returns matching lines with file paths.

WHEN TO USE: finding patterns across multiple files, locating function definitions,
  searching for imports, finding TODOs or error messages.

WHEN NOT TO USE: reading a known file (use read instead).
  Running commands (use bash instead).

DO NOT USE FOR: reading files (use read), listing directories (use bash),
  modifying files (use edit).

USAGE: pattern is a regex string. glob filters by file extension.
  Results are capped at 50 matches. If truncated, narrow your pattern or glob.

EXAMPLES:
  - Find all TODO comments: pattern "TODO" glob "*.ts"
  - Find function definitions: pattern "function \\w+" glob "*.ts"`,
  inputSchema: z.object({
    pattern: z.string(),
    path: z.string().optional(),
    glob: z.string().optional(),
  }),
  execute: async ({ pattern, path: searchPath, glob: globFilter }) => {
    // ... реализация поиска с лимитом 50 совпадений
  },
});
```

> **📝 Перевод промта** (поле `description` полностью):
>
> *«Ищи содержимое файлов по регулярному выражению. Возвращает совпавшие строки с путями к файлам.*
>
> *КОГДА ИСПОЛЬЗОВАТЬ: поиск паттернов по множеству файлов, нахождение определений функций, поиск импортов, нахождение TODO или сообщений об ошибках.*
>
> *КОГДА НЕ ИСПОЛЬЗОВАТЬ: чтение известного файла (используй read вместо этого). Запуск команд (используй bash вместо этого).*
>
> *НЕ ИСПОЛЬЗОВАТЬ ДЛЯ: чтения файлов (используй read), просмотра директорий (используй bash), изменения файлов (используй edit).*
>
> *ИСПОЛЬЗОВАНИЕ: pattern — это строка регулярного выражения. glob фильтрует по расширению файла. Результаты ограничены 50 совпадениями. Если вывод обрезан — сузь свой pattern или glob.*
>
> *ПРИМЕРЫ:*
> *- Найти все TODO-комментарии: pattern "TODO" glob "*.ts"*
> *- Найти определения функций: pattern "function \\w+" glob "*.ts"»*

### Зачем каждая секция

| Секция | Что делает | Пример |
|--------|-----------|--------|
| **Первая строка** | Говорит модели, **что** делает инструмент и **что возвращает** | «Ищи по regex, возвращай строки с путями» |
| `WHEN TO USE` | Конкретные сценарии с ключевыми словами из типичных запросов | «Поиск паттернов, определения функций, импорты» |
| `WHEN NOT TO USE` | **Мягко** перенаправляет к правильному инструменту, называя его по имени | «Читаешь файл? Используй read» |
| `DO NOT USE FOR` | **Жёстко** запрещает использовать инструмент не по назначению | «Никогда не используй для чтения файлов» |
| `USAGE` | Ограничения и поведение, которых не видно из схемы входа | «Лимит 50 совпадений, при обрезке — сузь поиск» |
| `EXAMPLES` | Конкретные вызовы — модель повторяет паттерн | `pattern "TODO" glob "*.ts"` |

### USAGE — ограничения, которых не видно из схемы

`inputSchema` описывает **форму** параметров: какие поля есть, какого они типа, обязательные ли. Но схема молчит о **поведении**:

- `z.string()` не скажет модели, что `pattern` — это regex, а не просто подстрока;
- схема не скажет, что вывод обрезается до 50 совпадений;
- схема не подскажет, что делать, если результат обрезан.

Всё это — в `USAGE`. Обрати внимание на последнее предложение: `If truncated, narrow your pattern or glob`. Это **инструкция на случай усечения**: модель узнаёт, что вывод может быть неполным, и что правильная реакция — сузить поиск, а не смириться с неполными данными.

Ключевой принцип: **всё, что модель не может вывести из схемы, должно быть написано словами.** Схема и описание дополняют друг друга: схема — про типы, описание — про смысл и поведение.

### EXAMPLES — конкретные вызовы

`EXAMPLES` — самая «механическая», но очень эффективная секция. Модель, увидев готовый пример `pattern "TODO" glob "*.ts"`, **копирует его структуру**, а не изобретает свою. Это снижает число ошибок в формате вызова — особенно у быстрых слабых моделей (Haiku), которые склонны путать имена и типы параметров.

Правила хороших примеров:

1. **Показывай реальные значения**, а не псевдокод. `pattern "TODO"` работает лучше, чем `pattern "<your pattern here>"`.
2. **Покрывай разные сценарии.** Один пример — простой поиск, второй — поиск с фильтром по расширению. Модель видит вариативность.
3. **Экранируй правильно.** В примере `pattern "function \\w+"` двойной обратный слэш `\\w` — это экранирование внутри JS-строки. Модель видит `\w` в итоговом тексте описания.

### Токены описаний кешируются между ходами

Один практичный факт, который делает секционированные описания *дешёвыми*. В каждом ходе агента (каждый вызов модели) инструменты с их описаниями **передаются заново**. Если описание — 300 токенов, а инструментов три, это ~900 токенов на каждый ход, умноженные на десятки ходов.

Но большинство провайдеров (Anthropic, OpenAI) поддерживают **prompt caching** — кеширование префикса промпта. Системный промпт и описания инструментов идут в начале запроса и **не меняются между ходами**, поэтому они попадают в кеш и при повторных вызовах стоят в разы дешевле (иногда на 90%).

Практический вывод: **не бойся писать подробные описания** — их токены в основном кешируются. Дороже всего обходится то, что *меняется* каждый ход (результаты инструментов, новые сообщения), а статичная часть — описания — дешёвая. Поэтому вкладываться в качество описаний выгодно: платишь один раз (при первом ходе), а пользу получаешь на каждом шаге.

### Полный пример: read с пятью секциями

Для полноты — тот же контракт, применённый к `read`:

```typescript
const read = tool({
  description: `Read a file from the working directory and return its contents as text.

WHEN TO USE: reading a known file path, inspecting source code,
  checking configuration, understanding a specific file.

WHEN NOT TO USE: searching across many files for a pattern (use grep instead).
  Running commands (use bash instead).

DO NOT USE FOR: searching code (use grep), executing commands (use bash),
  modifying files (use edit).

USAGE: path is relative to the working directory. Output is capped at 500 lines.
  If truncated, you can read a specific line range on the next call.

EXAMPLES:
  - Read package.json: path "package.json"
  - Read a source file: path "src/index.ts"`,
  inputSchema: z.object({
    path: z.string(),
  }),
  execute: async ({ path }) => {
    // ... чтение файла с лимитом 500 строк
  },
});
```

> **📝 Перевод промта** (поле `description`):
>
> *«Прочитай файл из рабочей директории и верни его содержимое как текст.*
>
> *КОГДА ИСПОЛЬЗОВАТЬ: чтение известного пути к файлу, изучение исходного кода, проверка конфигурации, понимание конкретного файла.*
>
> *КОГДА НЕ ИСПОЛЬЗОВАТЬ: поиск паттерна по множеству файлов (используй grep вместо этого). Запуск команд (используй bash вместо этого).*
>
> *НЕ ИСПОЛЬЗОВАТЬ ДЛЯ: поиска по коду (используй grep), выполнения команд (используй bash), изменения файлов (используй edit).*
>
> *ИСПОЛЬЗОВАНИЕ: path указывается относительно рабочей директории. Вывод ограничен 500 строками. Если вывод обрезан, ты можешь запросить конкретный диапазон строк в следующем вызове.*
>
> *ПРИМЕРЫ:*
> *- Прочитать package.json: path "package.json"*
> *- Прочитать файл исходников: path "src/index.ts"»*

Заметь симметрию: `read` и `grep` ссылаются друг на друга в секциях-перенаправлениях. `grep` говорит «читаешь файл → use read», `read` говорит «ищешь паттерн → use grep». Вместе они образуют связную **карту инструментов**, по которой модель ориентируется.

## Ключевые выводы

- **Описание — это API для модели.** Модель не видит код; всё, что она знает об инструменте, — это `description` и `inputSchema`. Пиши их как публичный интерфейс.
- **`USAGE` дополняет схему.** Всё, что не видно из `inputSchema` (лимиты, семантика значений, поведение при обрезке), должно быть написано словами.
- **`EXAMPLES` задают шаблон.** Конкретные вызовы с реальными значениями — модель копирует их, а не изобретает формат.
- **Негатив дублируется намеренно.** `WHEN NOT TO USE` (мягко) и `DO NOT USE FOR` (жёстко) покрывают модели разной мощности. Одного «не используй» почти всегда мало.
- **Инструменты ссылаются друг на друга.** Секции-перенаправления (`use read`, `use grep`) образуют карту, по которой модель маршрутизирует запросы.
- **Описания дешевле, чем кажутся.** Статичные токены описаний кешируются между ходами (prompt caching), поэтому подробные описания почти не влияют на стоимость повторных вызовов.
- **Дорого то, что меняется.** Результаты инструментов и новые сообщения — вот что реально стоит токенов. Именно их нужно ограничивать (bounded output), а не экономить на описаниях.

## Попробуй сам

1. **Допиши `USAGE` для всех инструментов.** У `read` и `bash` в твоём коде добавь секцию `USAGE` с лимитами и поведением. Проверь, что модель перестала «удивляться» обрезанным выводам.

2. **Добавь пример «что делать при обрезке».** В `USAGE` у `grep` убери фразу `If truncated, narrow your pattern or glob` и дай задачу с большим числом совпадений. Сравни: как модель ведёт себя с этой подсказкой и без неё.

3. **Проверь симметрию перенаправлений.** Прочитай описания `read` и `grep` как единый текст. Убедись, что каждый инструмент, упомянутый в чужом `WHEN NOT TO USE`, существует и назван точно тем же именем.

4. **Измерь размер описаний.** Посчитай токены описаний всех инструментов. Прикинь: сколько токенов уходит на описания при 30 ходах, и сколько из них кешируется. Убедись, что выгоднее потратить токены на качество описания, чем на повторные неудачные вызовы.

5. **Проведи A/B-тест описаний.** Возьми задачу «найди все TODO» и сравни два варианта `grep`: с одной строкой описания и с полным 5-секционным контрактом. Замерь, в скольких случаях из 10 модель выбирает `grep`, а не `bash` или `read`.
