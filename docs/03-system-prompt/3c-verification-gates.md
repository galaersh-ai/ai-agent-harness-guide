# Урок 3c: Гейты верификации — честность вместо покрытия

Дай агенту инструмент для запуска тестов — и он всё равно скажет «all tests pass», ни разу их не запустив. Это не злой умысел. Модели обучены на корпусах, где фраза «all tests pass» встречается очень часто, и подгоняют знакомый паттерн. Инструмент сам по себе проблему не решает — нужен **гейт верификации в промпте**: правила, которые заставляют агента честно разделять «я проверил» и «я надеюсь, что работает».

## Проблема

Классическая конфабуляция агента выглядит так:

- Агент изменил файл и пишет: **«All tests pass»** — но тесты не запускал. Их вообще может не быть в проекте.
- Агент пишет **«I fixed the bug»** — но проверил только, что TypeScript компилируется, а рантайм-поведение не трогал.
- Агент пишет **«The build works»** — но сборку не запускал, потому что в текущем режиме одобрения она была заблокирована.

Причина фундаментальная: модели обучены на текстах, где успех декларируется часто и уверенно. Паттерн «сделал → написал "работает"» статистически более вероятен, чем «сделал → запустил проверку → отчитался о реальном результате». Чтобы переломить этот сдвиг, промпт должен **активно сопротивляться**.

## Решение с кодом

Добавляем секцию `# Verification` в системный промпт:

```typescript
sections.push(`# Verification
After making changes, verify your work:
1. Run \`npx tsc --noEmit\` when TypeScript is present
2. Run lint, test, or build commands only if they exist in this project
   and are allowed by the current approval mode
3. Report exactly what you ran, what was blocked, and what was unavailable
4. Do NOT inflate partial verification into a blanket success claim

Do NOT claim "tests pass" without running them.
Scope your claims honestly. "Verification was limited because writes were blocked"
is honest. "All tests pass" when you didn't run them is not.`);
```

> **📝 Перевод промта:**
>
> *«После внесения изменений проверь свою работу:*
> *1. Запусти `npx tsc --noEmit`, если проект использует TypeScript*
> *2. Запускай lint, тесты или сборку только если они существуют в этом проекте и разрешены текущим режимом одобрения*
> *3. Отчитывайся точно: что запускал, что было заблокировано, что недоступно*
> *4. Не раздувай частичную проверку в заявление о полном успехе*
>
> *Не утверждай «тесты прошли», не запуская их.*
> *Ограничивай свои заявления честно. «Проверка была ограничена, потому что запись была заблокирована» — честно. «Все тесты прошли», когда ты их не запускал, — нет.»*

### Scoped claims: что агент может сказать vs что нужно

Ключевая идея секции — **scoped claims** (ограниченные, «скопированные» заявления). Агент не должен говорить «всё работает», он должен говорить, *что именно* он проверил и *что получил*:

| Может сказать (конфабуляция) | Нужно (честный отчёт) |
|---|---|
| «All tests pass» | «Ran npm test: 47 passed, 3 failed (pre-existing, unrelated to my change)» |
| «I fixed the bug» | «Fixed null check in auth.ts:42. npx tsc --noEmit passes. Tests blocked by approval.» |
| «The build works» | «Ran npm run build: succeeded in 4.2s, no warnings.» |

> **📝 Перевод промта (примеры честных отчётов):**
>
> *«Запустил npm test: 47 прошло, 3 упало (уже были, не связаны с моим изменением)»*
>
> *«Исправил проверку на null в auth.ts:42. `npx tsc --noEmit` проходит. Тесты заблокированы режимом одобрения.»*
>
> *«Запустил npm run build: собрался за 4.2с, без предупреждений.»*

Обрати внимание на структуру честного отчёта: **конкретная команда + конкретный результат + явное указание, что было недоступно**. Это и есть «scope» — рамки, внутри которых заявление истинно.

### Маркер конфабуляции

Есть простой эвристический признак, по которому можно отличить честный отчёт от выдуманного:

> Следи за мягкими фразами: **«should be fine»**, **«looks good to me»**, **«I expect this to work»**. Это маркеры. Модель, реально запустившая проверку, использует **прошедшее время и конкретный результат**. Не запустившая — уклончивое будущее время.

| Признак | Конфабуляция | Честный отчёт |
|---------|--------------|---------------|
| Время глагола | Будущее/условное: «should work», «ought to pass» | Прошедшее: «ran», «passed», «failed» |
| Конкретность | Абстрактно: «looks good» | Конкретно: «47 passed, 3 failed» |
| Источник | Нет ссылки на запуск | Есть команда, которую реально запускали |

Логика проста: проверка — это событие в прошлом. Если агент её запускал, он говорит о ней в прошедшем времени с конкретным результатом. Если он про неё *рассуждает*, он говорит о ней в будущем или условном наклонении.

### Почему это гейт, а не пожелание

Секция `# Verification` — это **гейт**, потому что она меняет контракт отчёта. Агент больше не может просто «завершить» задачу — он обязан пройти через точку проверки и отчитаться по правилам. Причём гейт стоит именно в промпте, а не в коде: код не может проверить, *честен* ли агент (он видит только строку ответа), а промпт может *потребовать* честности.

## Ключевые выводы

- **Инструмент проверки ≠ честный отчёт.** Модель выдумает результат, если промпт не сопротивляется — фраза «all tests pass» статистически притягательна.
- **Scoped claims** — заявляй ровно то, что проверил: конкретная команда + конкретный результат + что было недоступно.
- **Маркер конфабуляции:** «should be fine», «looks good», «I expect» — будущее время. Честный отчёт — прошедшее время + конкретика.
- **«Do NOT inflate partial verification»** — частичная проверка не равна полному успеху.
- Гейт верификации стоит **в промпте**, потому что честность — свойство поведения, а не кода.

## Попробуй сам

1. Дай агенту задачу «исправь баг и проверь» в проекте без тестов. Без секции `# Verification` и с ней — сравни, как меняется финальный отчёт.
2. Попроси агента изменить файл и запрети (через режим одобрения) запуск тестов. Проверь: честно ли он скажет «тесты заблокированы», или соврёт «всё работает».
3. Напиши список из 10 фраз-маркеров конфабуляции («should be fine», «looks good», …) и добавь их в свои ревью — научись ловить их в ответах агента.
4. Добавь в `# Verification` пятый пункт: требование указывать **команду**, которую агент запускал для проверки.
