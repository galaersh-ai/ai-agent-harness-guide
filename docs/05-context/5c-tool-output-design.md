# Урок 5c: Проектирование вывода инструментов (bounded output)

Обрезка из прошлого урока убирает **старые** результаты. Но если один-единственный результат — 5000 токенов, ущерб уже нанесён: этот кусок загрязняет контекст на всех шагах, пока его не отсечёт pruning. Лучший фикс — **выше по потоку**: инструменты должны выдавать **ограниченный вывод по умолчанию**. В этом уроке мы спроектируем лимиты вывода и — что важнее — контракт усечения, который делает усечение видимым для модели.

## Проблема

Посмотри, что происходит без ограничений:

- Агент вызывает `read` на файле в 10 000 строк. Весь файл попадает в контекст. Агенту нужно было понять структуру — достаточно было 500 строк.
- Агент вызывает `grep` и получает 500 совпадений. Ему нужны были первые 50, чтобы ответить на вопрос. Остальные 450 — дамп данных.
- Агент вызывает `bash` с `npm install`, и вывод — несколько тысяч строк шума. Агенту нужна только последняя строка: «installed 234 packages».

Каждый неограниченный результат — это **единоразовый удар** по контексту, который потом долго живёт в памяти. И суммарно это тот самый линейный рост входа, который мы измеряли в уроке 5a. Обрезка чистит хвост истории, но не спасает от единичного гигантского результата.

## Решение с кодом

### Лимиты по инструментам

Каждому инструменту — свой лимит, подобранный под его природу:

| Инструмент | Лимит | Почему именно столько |
|-----------|-------|----------------------|
| `read` | 500 строк | Достаточно понять структуру файла; 10 000 строк — загрязнение |
| `grep` | 50 совпадений | 50 результатов ответили на вопрос; 500 — дамп данных |
| `bash` | 5000 символов | Большинство выводов помещается; `npm install` даёт шум |

### Реализация `read` — 500 строк

```typescript
const MAX_READ_LINES = 500;

execute: async ({ path }) => {
  const content = await sandbox.readFile(path);
  const lines = content.split("\n");
  if (lines.length <= MAX_READ_LINES) return content;
  const head = lines.slice(0, MAX_READ_LINES).join("\n");
  return `${head}\n... (truncated: ${lines.length - MAX_READ_LINES} more lines)`;
}
```

### Реализация `grep` — 50 совпадений

```typescript
const MAX_GREP_MATCHES = 50;

// в цикле поиска:
if (matches.length >= MAX_GREP_MATCHES) {
  matches.push(`... (truncated: more matches exist, refine your pattern)`);
  break;
}
```

### Реализация `bash` — 5000 символов, хранить хвост

Ключевая тонкость именно у `bash`: при усечении хранить **хвост**, а не голову:

```typescript
const MAX_BASH_CHARS = 5000;

const stdout = result.stdout || "(no output)";
const cappedStdout =
  stdout.length > MAX_BASH_CHARS
    ? stdout.slice(-MAX_BASH_CHARS) +
      `\n... (truncated, showing last ${MAX_BASH_CHARS} chars)`
    : stdout;
```

Почему хвост: **ошибки обычно в конце**. Упавший тест печатает ошибки последними, упавшая сборка — ошибку последней. Храня хвост, хранишь ту часть, на которую агенту нужно реагировать. Если бы мы хранили голову (`slice(0, MAX)`), то у `npm test` агент видел бы список пройденных тестов и **не видел бы упавший** — и честно сообщил бы «всё прошло», хотя в хвосте была ошибка.

### Контракт усечения — видимое сообщение для модели

Самое важное правило этого урока: **каждое усечение выдаёт видимое сообщение** для модели.

```
... (truncated, showing last 5000 chars)
... (truncated: 9500 more lines)
... (truncated: more matches exist, refine your pattern)
```

Почему это критично:

- Модель **видит**, что результат неполный, и может **пагинировать** — запросить следующую порцию (например, `read` со смещением, или `grep` с уточнённым паттерном).
- Инструмент, который **молча усекает**, хуже отсутствия усечения: модель думает, что видит полную картину, и принимает решения на неполных данных.

Это и есть **контракт усечения**: усечение обязано быть *явным и видимым*, а не тихим. Модель — участник контракта, и она должна знать, когда данные обрезаны.

### Усечение vs обрезка

Подведём итог по двум механизмам модуля:

| Механизм | Что убирает | Где | Когда |
|----------|-------------|-----|-------|
| **Bounded output** (этот урок) | Лишнюю часть **одного** результата | Внутри инструмента | Сразу при генерации |
| **Pruning** (урок 5b) | **Старые** результаты целиком | В `prepareCall` | Перед отправкой модели |

Bounded output — профилактика (не дать гиганту родиться), pruning — лечение (выбросить накопленное). Оба нужны: лимиты не спасут от линейного накопления истории, а обрезка не спасёт от единичного 5000-токенного результата.

## Ключевые выводы

- **Лимиты по инструментам:** `read` — 500 строк, `grep` — 50 совпадений, `bash` — 5000 символов. Каждый лимит обоснован природой инструмента.
- **`bash` хранит хвост, не голову** — ошибки в конце, и агент должен видеть именно их.
- **Контракт усечения:** каждое усечение — видимое сообщение (`... (truncated, ...)`), чтобы модель знала о неполноте и могла пагинировать.
- **Молчаливое усечение хуже отсутствия усечения** — модель думает, что видит всё.
- **Bounded output = профилактика**, **pruning = лечение**; нужны оба.
