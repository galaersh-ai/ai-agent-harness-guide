# Урок 5d: Кеширование контекста (cache control)

Обрезка и лимиты сокращают **объём** контекста. Но есть и вторая ось оптимизации — **стоимость**. Даже после обрезки стабильный префикс разговора (системный промпт, исходная задача, ранние сообщения) отправляется модели на **каждом** шаге заново — и за каждый токен ты платишь. Решение — **кеширование контекста (prompt caching)**: пометить стабильный префикс как кешируемый, чтобы провайдер не пересчитывал его повторно. Счёт за сессию падает в разы.

## Проблема

Посмотри, что модель получает на каждом шаге после обрезки:

```
[system prompt]                    ← одинаковый на ВСЕХ шагах
[user prompt]                      ← одинаковый на ВСЕХ шагах
[assistant + tool_call] → [result] ← недавние, меняются
[assistant + tool_call] → [result] ← недавние, меняются
```

Первые два блока — **стабильный префикс**: он не меняется от шага к шагу. Но без кеширования провайдер обрабатывает его заново на **каждом** вызове:

- Шаг 1: система обрабатывает префикс из 30 000 токенов.
- Шаг 2: система снова обрабатывает **те же** 30 000 токенов + новое.
- Шаг 3: снова те же 30 000 + новое…

Ты платишь за обработку одного и того же текста десятки раз. Для агента с 50 шагами и префиксом в 30 000 токенов это выливается в ощутимый счёт — хотя реально нового контента в каждом шаге немного.

## Решение с кодом

Помечаем стабильный префикс как **ephemeral** (кешируемый) через `cache_control`. Вспомогательная функция:

```typescript
function addCacheControl(messages: ModelMessage[], system: string) {
  // Системный промпт — самый стабильный блок, кешируем целиком
  const systemWithCache = [
    {
      role: "system",
      content: system,
      cache_control: { type: "ephemeral" },
    },
  ];

  // Сообщения, кроме последних двух, — стабильный префикс
  const messagesWithCache = messages.map((msg, i) => {
    if (i >= messages.length - 2) return msg;      // недавние НЕ кешируем
    return { ...msg, cache_control: { type: "ephemeral" } };
  });

  return { system: systemWithCache, messages: messagesWithCache };
}
```

> **📝 Комментарий:**
>
> *`cache_control: { type: "ephemeral" }` — это аннотация для провайдера (Anthropic prompt caching): «этот блок можно кешировать». Кешируемые блоки провайдер вычисляет один раз и переиспользует на последующих шагах, пока префикс не изменится. «Ephemeral» означает, что кеш живёт ограниченное время (обычно 5–10 минут неактивности) и не хранится постоянно.*

### Ключевые правила

1. **Стабильный префикс помечаем, недавнее — нет.** Последние 1–2 сообщения меняются каждый шаг (туда попадают новые результаты инструментов), поэтому кешировать их бессмысленно: префикс для кеша должен быть **непрерывным от начала** и неизменным.

2. **Системный промпт кешируется всегда.** Это самый стабильный блок — он не меняется на протяжении всей сессии.

3. **Кеш работает, пока префикс не изменился.** Как только начало разговора меняется (например, обрезка выбросила раннее сообщение), кеш сбрасывается и префикс вычисляется заново. Поэтому `addCacheControl` лучше вызывать **после** `pruneMessages` (урок 5b): сначала стабилизируем префикс, потом кешируем.

### Подключение в коде

```typescript
import { addCacheControl } from "./cache";

const agent = new ToolLoopAgent({
  model: "anthropic/claude-haiku-4-5",
  instructions,
  tools,
  prepareCall: async (options) => {
    const pruned = {
      ...options,
      messages: options.messages
        ? pruneMessages({
            messages: options.messages,
            toolCalls: "before-last-3-messages",
          })
        : undefined,
    };

    const cached = addCacheControl(pruned.messages ?? [], instructions);
    return {
      ...pruned,
      messages: cached.messages,
      // system передаётся провайдеру с cache_control
    };
  },
});
```

Порядок важен: **сначала обрезка, потом кеширование**. Обрезка фиксирует стабильный префикс; кеширование помечает его как ephemeral. Если поменять местами — кеш будет сбрасываться на каждом шаге, и выгода пропадёт.

### Эффект: счёт за сессию падает в разы

Prompt caching кардинально снижает стоимость **входных** токенов. Кешированные токены у провайдеров стоят в разы дешевле обычных:

```
Без кеширования: ~$30 за сессию
С кешированием:  ~$6 за сессию
```

Разница — в 5 раз, и тем больше, чем длиннее сессия и чем больше стабильный префикс. Это не «экономия на мелочах», а отдельный архитектурный слой оптимизации: **объём** контекста сокращаем обрезкой и лимитами (уроки 5b, 5c), **стоимость** — кешированием (этот урок).

### Полная картина модуля 5

| Урок | Ось | Механизм | Эффект |
|------|-----|----------|--------|
| 5a | Диагноз | `onStepFinish` + `usage` | Видим проблему |
| 5b | Объём | `pruneMessages` | Кривая выходит на плато |
| 5c | Объём | Лимиты вывода | Нет гигантских результатов |
| 5d | Стоимость | `cache_control` | Счёт падает ~5× |

## Ключевые выводы

- **`addCacheControl()` помечает стабильный префикс как `ephemeral`** — провайдер вычисляет его один раз и переиспользует.
- **Недавние 1–2 сообщения не кешируются** — они меняются каждый шаг, кешировать их бессмысленно.
- **Системный промпт кешируется всегда** — он неизменен на протяжении сессии.
- **Порядок: сначала обрезка, потом кеширование** — обрезка стабилизирует префикс, иначе кеш сбрасывается каждый шаг.
- **Эффект: ~$30 → ~$6 за сессию** — кешированные входные токены стоят в разы дешевле.

## Попробуй сам

1. Реализуй `addCacheControl` и проверь, что системный промпт и ранние сообщения получают `cache_control: { type: "ephemeral" }`, а последние два — нет.
2. Подключи кеширование **до** обрезки и **после** неё — сравни, в каком случае префикс остаётся стабильным (и кеш работает).
3. Замерь стоимость сессии с кешированием и без (по логам `usage` и тарифу провайдера) — подтверди падение счёта примерно в 5 раз.
4. Убедись, что при изменении префикса (например, обрезка выбросила раннее сообщение) кеш сбрасывается — и подумай, как минимизировать такие сбросы.
