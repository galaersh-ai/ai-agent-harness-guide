    Урок 3d: Проектный контекст — AGENTS.md

    Каркас агента общий, а проекты — разные. Один использует bun test, другой vitest, третий npm run check. Один — монорепо с пакетами, другой — плоский сервис. Один пишет функциональные компоненты с именованными экспортами, другой — классы. Агент не должен угадывать всё это — проект должен сам рассказать о себе. В этом уроке мы научим каркас читать файл AGENTS.md и вставлять его содержимое в системный промпт.

    Проблема

    У агента есть общие правила (Agency, Guardrails, Verification) — но они ничего не знают о конкретном проекте. Из-за этого агент:

    • Запускает npm test, хотя в проекте принят bun test — команда падает или вообще отсутствует.
    • Угадывает архитектуру: «наверное, это обычный Node-проект», тогда как перед ним монорепо с пакетами в packages/.
    • Пишет код в неверном стиле: export default, когда в проекте приняты именованные экспорты.

    Эти знания нельзя вывести из кода автоматически — точнее, выводить их дорого и ненадёжно. Проще, если проект сам их декларирует. Но как донести их до агента, не захардкоживая под каждый проект?

    Решение с кодом

    Кладём markdown-файл AGENTS.md в корень проекта. Каркас читает его при старте и передаёт в buildSystemPrompt (из урока 3b) как projectContext:

    import { existsSync, readFileSync } from "node:fs";
import { join } from "node:path";

const agentsPath = join(cwd, "AGENTS.md");
const projectContext = existsSync(agentsPath)
  ? readFileSync(agentsPath, "utf-8")
  : undefined;

const instructions = buildSystemPrompt({
  workingDirectory: cwd,
  sandboxType: "local",
  toolNames: Object.keys(tools),
  projectContext,   // содержимое AGENTS.md или undefined
});

    Механика простая и идиоматичная для Node.js:

    • existsSync — проверяем, есть ли файл вообще. Нет файла → нет и секции в промпте (в buildSystemPrompt стоит if (ctx.projectContext)).
    • readFileSync(path, "utf-8") — читаем целиком как строку.
    • Результат — либо строка с содержимым, либо undefined. Второй вариант означает «проект ничего о себе не рассказал».

    Что класть в AGENTS.md

    Файл — это конвенция, а не конфигурация: структура свободная, но есть проверенные секции:

    # Project Instructions

## Commands
- `bun test` runs the test suite
- `bun run build` builds for production
- `bun run lint` checks code style

## Architecture
- Monorepo, packages live in `packages/`
- Each package has its own `tsconfig.json`
- Shared types in `packages/shared/`

## Style
- Functional components, no classes
- Named exports, not default
- Error messages must be user-facing

## Lessons learned
- Auth middleware must run before rate limiting
- Don't modify migration files directly, generate new ones

    📝 Перевод промта:

    Этот файл — аналог CONTRIBUTING.md для людей, но адресованный AI-агенту. Он содержит информацию, которую каркас не может вывести из кода: какие команды использовать, как устроена архитектура, какой стиль принят, какие ошибки повторяются.

    Перевод секций:

    # Project Instructions — «Инструкции проекта».

    ## Commands — «Команды»: «bun test запускает тесты; bun run build собирает для продакшена; bun run lint проверяет стиль кода.»

    ## Architecture — «Архитектура»: «Монорепо, пакеты лежат в packages/; у каждого пакета свой tsconfig.json; общие типы — в packages/shared/».

    ## Style — «Стиль»: «Функциональные компоненты, без классов; именованные экспорты, не default; сообщения об ошибках должны быть обращены к пользователю.»

    ## Lessons learned — «Извлечённые уроки»: «Auth-мидлварь должна выполняться до rate limiting; не меняй файлы миграций напрямую — генерируй новые.»

    Назначение секций

    Секция Что решает
    Commands Какие команды реально существуют — агент перестаёт угадывать npm test vs bun test
    Architecture Как устроен код — где пакеты, где общие типы
    Style Какие соглашения приняты — чтобы новый код не выбивался
    Lessons learned Накопленные грабли — чтобы агент не наступал на них повторно

    Секция Lessons learned особенно ценна: это память проекта, которая переживает смену моделей и разработчиков. Сюда пишут то, что однажды уже отладили кровью.

    Знакомый паттерн с разными именами

    Идея «обнаружить markdown-файл → вставить как инструкции» — общая для всей индустрии. Меняется только имя файла:

    Инструмент Имя файла
    Cursor .cursorrules
    Codex AGENTS.md
    Claude Code CLAUDE.md
    pi своя конвенция

    Имя разное, паттерн один. Это признак того, что конвенция «проект сам рассказывает о себе» — проверенное временем решение, а не выдумка одного каркаса.

    Почему конвенция, а не конфигурация

    AGENTS.md — это конвенция (свободный markdown, читает человек и машина), а не конфигурация (строгая схема, config.json). Разница важна:

    • Конфигурацию нужно валидировать, документировать её схему, обрабатывать ошибки парсинга.
    • Конвенцию достаточно прочитать как текст и вставить. Ошибок парсинга нет — любой markdown валиден.

    Для задачи «рассказать агенту о проекте» строгая схема — избыточна. Свободный текст делает то же самое проще, и его может написать любой разработчик без чтения документации.

    Ключевые выводы

    • Проект сам рассказывает о себе через AGENTS.md — агент перестаёт угадывать команды, архитектуру и стиль.
    • existsSync + readFileSync — вся механика: нет файла → нет секции, есть файл → читаем и вставляем.
    • Четыре проверенные секции: Commands, Architecture, Style, Lessons learned.
    • Lessons learned — память проекта, переживающая смену моделей и людей.
    • Паттерн общий для индустрии: Cursor (.cursorrules), Codex (AGENTS.md), Claude Code (CLAUDE.md). Один приём, разные имена.
    • Конвенция проще конфигурации: свободный markdown без схемы и валидации делает задачу лучше.

    Попробуй сам

    1. Создай AGENTS.md для своего проекта с четырьмя секциями и подключи чтение в каркас. Запусти агента — проверь, что он использует правильные команды из Commands.
    2. Убери AGENTS.md и убедись, что секция # Project Instructions исчезает из промпта (условие if (ctx.projectContext)).
    3. Добавь в Lessons learned реальную граблю из твоего проекта и проверь, избегает ли её агент.
    4. Запиши, какое из имён (AGENTS.md, CLAUDE.md, .cursorrules) использует твой основной AI-инструмент — и подумай, стоит ли поддерживать несколько имён в каркасе.
