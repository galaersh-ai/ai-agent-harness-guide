    Урок 6: Шлюзы одобрения — от boolean к discriminated union

    Разбор курса «Build Your Own AI Coding Agent Harness» от Vercel Academy (автор — Joel Hooks). Перевод и адаптация на русский.

    Что узнаем в этом уроке

    В уроке 3 мы построили allowlist — жёсткий шлюз «разрешено/заблокировано» с одним-единственным режимом. Но реальный каркас живёт в разных контекстах: локальная разработка, CI-пайплайн, субагенты. В каждом из них вопрос «можно ли выполнить эту команду?» решается по-разному.

    В этом уроке мы пройдём эволюцию конфигурации одобрения в три этапа: от бесполезного boolean, через негибкую функцию, к правильной форме — discriminated union. Мы научимся: - различать три режима: interactive, background, delegated; - строить фабрику createApproval(config), возвращающую функцию-предикат; - понимать, почему конфиг должен быть данными, а не кодом — ради Zod-валидации, сериализации и передачи через границу субагента.

    Проблема — что не работает и почему

    Allowlist имеет ровно один режим

    Наш текущий шлюз — это isSafe(), сверяющая команду с SAFE_PREFIXES:

    function isSafe(command: string): boolean {
  return SAFE_PREFIXES.some((p) => command.trim().startsWith(p));
}

    Логика простая: в списке — можно, нет — блокируем. Но у реального каркаса три разных контекста, и один режим их не покрывает:

    Контекст Особенность Что нужно
    Локальная разработка Есть человек у терминала Опасные команды — спрашивать человека
    CI / автоматизация Человека нет, всё должно крутиться само Одобрять всё автоматически
    Субагент Подчинённый агент с частичным доверием Разрешить только узкий список

    Один SAFE_PREFIXES не различает эти случаи. В CI нет человека, чтобы спросить — и агент просто застрянет на первой же «небезопасной» команде. Субагенту нельзя давать весь allowlist родителя — он должен получить лишь часть. А локальному пользователю хочется одобрить npm install express один раз и не отвечать снова.

    Три наивных подхода и почему они не годятся

    Подход 1 — boolean. Просто needsApproval: true или false:

    needsApproval: true   // блокирует ВСЁ. Бесполезно

    Одно значение на весь инструмент. Либо блокируем всё (агент парализован), либо разрешаем всё (безопасности нет). Никакой градации. Тупик.

    Подход 2 — функция. Правило, зашитое в код:

    needsApproval: ({ command }) => {
  if (SAFE_PREFIXES.some((p) => command.startsWith(p))) return false;
  return true;
}

    Лучше — есть логика. Но правило зашито намертво: CI получает тот же шлюз, что и локальный терминал. Перенастроить без переписывания кода нельзя. Конфигурация слилась с реализацией.

    Подход 3 — discriminated union. Конфиг как отдельная структура данных с несколькими вариантами. Это и есть правильная форма — разберём ниже.

    Решение — подход с полным кодом

    Этап 1: Boolean (тупик, фиксируем для истории)

    Первый инстинкт — добавить булев флаг. Быстро, но бесполезно:

    const bash = tool({
  // ...
  needsApproval: true,   // блокирует ВСЁ, независимо от команды
  execute: async ({ command }) => { /* ... */ },
});

    true блокирует даже git status, false пропускает даже rm -rf. Нет промежуточных состояний. К тому же это возвращает нас к ловушке из урока 3: needsApproval — сигнал, а не шлюз. Булев флаг не даёт ни гибкости, ни реальной защиты. Отбрасываем.

    Этап 2: Функция (лучше, но не конфигурируемо)

    Функция-предикат принимает команду и возвращает true (нужно одобрение) или false (можно выполнять):

    needsApproval: ({ command }) => {
  if (SAFE_PREFIXES.some((p) => command.startsWith(p))) return false;
  return true;
}

    Это уже работает: безопасные команды проходят автоматически, остальные требуют одобрения. Но правило зашито в код. CI-пайплайн, которому нужно одобрять всё автоматически, получит тот же предикат — и застрянет. А чтобы дать субагенту другой список доверия, придётся писать вторую функцию и дублировать логику. Конфигурация не отделена от кода — а значит, не может быть ни сохранена, ни передана, ни провалидирована.

    Этап 3: Discriminated union (правильная форма)

    Выносим конфигурацию в тип-объединение с дискриминатором. Дискриминатор — это поле mode, которое однозначно определяет, какая из веток активна:

    type ApprovalConfig =
  | { mode: "interactive" }                     // человек решает
  | { mode: "background" }                      // авто-одобрение (CI)
  | { mode: "delegated"; trust: string[] };     // субагент с trust-листом

    Три варианта, различаемые полем mode:

    • interactive — локальная разработка. Безопасные команды выполняются автоматически, опасные — спрашивают человека.
    • background — CI / автоматизация. Человека нет, поэтому всё выполняется автоматически.
    • delegated — субагент. Выполняется только то, что входит в trust-список, переданный родителем.

    Фабрика createApproval

    Фабрика принимает конфиг и возвращает функцию-предикат — ту самую, которую мы подставим вместо зашитой логики:

    function createApproval(config: ApprovalConfig) {
  return ({ command }: { command: string }): boolean => {
    if (config.mode === "background") return false;   // всё разрешено

    if (config.mode === "delegated") {
      // разрешено только то, что в trust-списке
      return !config.trust.some((p) => command.trim().startsWith(p));
    }

    // interactive: безопасное — автоматически, остальное — спросить человека
    return !SAFE_PREFIXES.some((p) => command.trim().startsWith(p));
  };
}

    Разберём по веткам:

    background — возвращает false всегда. «Одобрение не требуется» для любой команды. Это режим CI: нет человека, который мог бы ответить, поэтому доверяем полностью (и принимаем этот риск осознанно).

    delegated — возвращает false (не требует одобрения) только если команда начинается с одного из префиксов в trust. Всё остальное — true (заблокировано). Субагент получает ровно столько доверия, сколько родитель решил передать.

    interactive — возвращает false для безопасных команд (из глобального SAFE_PREFIXES) и true для остальных. Это наш старый allowlist, но теперь он — один из трёх режимов, а не единственный.

    Заметь: createApproval возвращает функцию, а не значение. Это значит, что проверка происходит при каждом вызове, с актуальной командой — и конфиг можно создать один раз, а использовать многократно.

    Подключение к инструменту

    Теперь фабрика createBashTool из прошлого урока принимает предикат одобрения вместо жёсткого списка префиксов:

    function createBashTool(
  operations: BashOperations,
  needsApproval: (input: { command: string }) => boolean
) {
  return tool({
    description: `Execute a shell command in the working directory.
WHEN TO USE: running build commands, installing packages, running tests,
  git operations, directory listings.
WHEN NOT TO USE: reading file contents (use read instead).
  Searching for patterns (use grep instead).
DO NOT USE FOR: reading files (use read), searching code (use grep).`,
    inputSchema: z.object({
      command: z.string().describe("Shell command to execute"),
    }),
    execute: async ({ command }) => {
      if (needsApproval({ command })) {
        return `Blocked: "${command}" requires approval.`;
      }
      const { stdout, exitCode } = await operations.exec(command);
      return stdout || (exitCode !== 0 ? `(exited ${exitCode})` : "(no output)");
    },
  });
}

    📝 Перевод промта (поле description):

    «Выполни shell-команду в рабочей директории.

    КОГДА ИСПОЛЬЗОВАТЬ: запуск сборки, установка пакетов, запуск тестов, git-операции, просмотр списка файлов в директории.

    КОГДА НЕ ИСПОЛЬЗОВАТЬ: чтение содержимого файлов (используй read вместо этого). Поиск паттернов (используй grep вместо этого).

    НЕ ИСПОЛЬЗОВАТЬ ДЛЯ: чтения файлов (используй read), поиска по коду (используй grep).»

    Ключевое отличие от урока 3: шлюз по-прежнему внутри execute. Предикат needsApproval лишь решает, а инструмент по-прежнему возвращает строку Blocked: ... при блокировке. Мы не вернулись к опции needsApproval из AI SDK — мы по-прежнему гарантируем, что модель всегда получает строку.

    Три режима на месте вызова

    Вот как один и тот же инструмент собирается для трёх разных контекстов:

    // Локальная разработка: человек одобряет опасные команды
const bash = createBashTool(
  localOps,
  createApproval({ mode: "interactive" })
);

// CI / автоматизация: всё выполняется автоматически
const bash = createBashTool(
  localOps,
  createApproval({ mode: "background" })
);

// Субагент: наследует только часть доверия от родителя
const bash = createBashTool(
  localOps,
  createApproval({
    mode: "delegated",
    trust: ["npm test", "npm run build", "npx tsc"],
  })
);

    📝 Комментарий переводчика (про режим delegated):

    Режим delegated со списком trust: ["npm test", "npm run build", "npx tsc"] означает: субагент может запускать тесты, сборку и проверку типов, но не может устанавливать пакеты, не может модифицировать файлы напрямую, не может запускать произвольные команды. Список доверия намеренно мал.

    Почему именно discriminated union

    Можно спросить: зачем городить union, если можно написать три отдельные функции? Ответ — конфиг это данные, а не код. Данные можно:

    1. Валидировать через Zod. Конфиг приходит извне (файл, переменная окружения, граница субагента) — его нужно проверить до использования:
    import { z } from "zod";

const approvalConfigSchema = z.discriminatedUnion("mode", [
  z.object({ mode: z.literal("interactive") }),
  z.object({ mode: z.literal("background") }),
  z.object({ mode: z.literal("delegated"), trust: z.array(z.string()) }),
]);

const config = approvalConfigSchema.parse(rawConfigFromEnv);

    z.discriminatedUnion проверяет, что поле mode — одно из допустимых, и что для delegated обязательно присутствует trust. Невалидный конфиг отбрасывается до того, как попадёт в фабрику.

    1. Сериализовать и передавать через границу субагента. Родитель создаёт субагента, передавая ему конфиг как обычный JSON: { mode: "delegated", trust: [...] }. Это невозможно с функцией — функцию не сериализуешь в JSON.

    2. Хранить в файле AGENTS.md или в конфигурации проекта. Конфиг читается из файла, валидируется и применяется — без правки кода каркаса.

    3. Менять режимы без переписывания кода. Переключение с interactive на background — это замена данных, а не логики.

    Бонус: безопасность на уровне типов. TypeScript сужает config.trust до string[] только внутри ветки if (config.mode === "delegated"). Попытка обратиться к config.trust в ветке interactive — ошибка компиляции. Boolean и обычная функция такой защиты не дают: там trust пришлось бы объявлять опциональным и проверять вручную (и о нём легко забыть).

    Полная картина: конфиг → предикат → шлюз

    ApprovalConfig (данные)
      │
      │  createApproval()  — фабрика превращает данные в поведение
      ▼
needsApproval (функция-предикат)
      │
      │  подставляется в createBashTool
      ▼
шлюз внутри execute  — модель всегда получает строку

    Конфиг описывает политику (что разрешено), фабрика превращает политику в механизм (проверку), а механизм встраивается в инструмент так, чтобы модель никогда не оставалась без ответа.

    Ключевые выводы

    • Один режим allowlist не покрывает реальность. Локальная разработка, CI и субагенты требуют разных политик одобрения.
    • Boolean — тупик. true блокирует всё, false разрешает всё. Нет градации, нет гибкости.
    • Функция — лучше, но не конфигурируемо. Правило зашито в код: CI получает тот же шлюз, что и локальный терминал, перенастроить нельзя.
    • Discriminated union — правильная форма. Поле mode однозначно выбирает ветку: interactive, background или delegated.
    • createApproval(config) возвращает функцию. Политика описывается данными, а проверка выполняется при каждом вызове с актуальной командой.
    • Конфиг — это данные, а не код. Его можно валидировать через Zod, сериализовать в JSON и передавать через границу субагента.
    • TypeScript сужает типы по дискриминатору. config.trust доступен только в ветке delegated — ошибки ловятся на этапе компиляции.
    • Шлюз по-прежнему внутри execute. Предикат решает, инструмент возвращает строку. Модель никогда не остаётся без результата.

    Попробуй сам

    1. Пройди эволюцию сам. Начни с needsApproval: true и посмотри, как агент блокирует даже git status. Затем перейди к функции, затем к discriminated union. Зафиксируй, на каком этапе что ломается.

    2. Собери три конфигурации. Создай три экземпляра bash с режимами interactive, background и delegated. Для каждого проверь, какие команды выполняются, а какие блокируются.

    3. Проверь trust-лист. Дай субагенту trust: ["npm test"]. Попроси его запустить тесты (должно сработать) и установить пакет (должно заблокироваться).

    4. Добавь Zod-валидацию. Прочитай конфиг из переменной окружения (JSON-строка) и провалидируй через z.discriminatedUnion. Проверь, что невалидный mode отбрасывается до попадания в фабрику.

    5. Попробуй сломать типы. Обратись к config.trust в ветке interactive. Убедись, что TypeScript выдаёт ошибку компиляции — и что это именно та защита, которую boolean и функция не давали.
