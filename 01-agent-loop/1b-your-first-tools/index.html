    Урок 2: Первые инструменты — grep и проблема выбора

    Разбор курса «Build Your Own AI Coding Agent Harness» от Vercel Academy (автор — Joel Hooks). Перевод и адаптация на русский.

    Что узнаем в этом уроке

    В прошлом уроке мы дали агенту один инструмент read — и он научился честно отвечать о содержимом файлов. Но настоящая работа с кодом требует большего: «найди, где объявлена эта функция», «покажи все TODO», «где импортируется этот модуль?». Для этого нужен поиск — инструмент grep.

    В этом уроке мы: - поймём проблему выбора инструмента — почему, когда инструментов несколько, модель выбирает неправильный; - познакомимся с «гравитацией bash» — эффектом, из-за которого все модели тянутся к универсальному инструменту; - изучим 4-секционный контракт описания инструмента: WHEN TO USE, WHEN NOT TO USE, DO NOT USE FOR, EXAMPLES; - напишем инструмент grep с лимитом в 50 совпадений.

    Проблема — что не работает и почему

    Больше инструментов — больше выбора — больше ошибок

    Пока инструмент один, выбора нет: модель вызывает read или отвечает сама. Но стоит добавить второй инструмент, как возникает задача маршрутизации: модель должна решить, какой инструмент подходит под запрос. И здесь начинаются проблемы.

    Представь агента с тремя инструментами: read (читает файл), grep (ищет по содержимому) и bash (выполняет команды). Пользователь пишет: «найди, где определена функция formatUser». Правильный выбор — grep. Но модель может выбрать read (наугад открыть какой-нибудь файл), а может — и это самое частое — выбрать bash и выполнить grep -r formatUser ..

    Bash gravity — гравитация bash

    Эффект, который наблюдают все разработчики агентов: все модели — Haiku, Sonnet, Opus — тяготеют к bash, когда описания других инструментов слабые. Причина проста: bash — самый универсальный инструмент. Им можно сделать что угодно: читать, искать, менять, удалять. Поэтому при малейшей неоднозначности модель по умолчанию «падает» в bash, как яблоко падает на землю.

    Чем это плохо:

    1. Потеря безопасности. У grep мы можем жёстко ограничить поведение (лимит совпадений, запрет на запись). bash — чёрный ящик, контролировать его сложнее.
    2. Потеря семантики. Когда модель вызывает grep-инструмент, мы в коде знаем, что она ищет. Когда она вызывает bash -c "grep ...", нам приходится парсить строку команды, чтобы понять намерение.
    3. Непредсказуемость. bash может натворить что угодно: rm -rf, перезапись файлов, установка пакетов.

    Решение — не запрещать bash, а сделать так, чтобы модель хотела выбирать правильный инструмент. И делается это через описание.

    Решение — подход с полным кодом

    Контракт описания: четыре секции

    Слабое описание — одна фраза типа "Search files.". Модели этого недостаточно, чтобы принять осознанное решение. Вместо этого описание инструмента строится как контракт из четырёх секций:

    Секция Назначение
    WHEN TO USE Конкретные сценарии, где инструмент — правильный выбор. Ключевые слова из типичных запросов пользователя.
    WHEN NOT TO USE Мягко перенаправляет к правильному инструменту, называя его по имени.
    DO NOT USE FOR Жёстко запрещает использовать инструмент не по назначению.
    EXAMPLES Конкретные примеры вызовов — модель повторяет показанный паттерн.

    Первая строка описания (до секций) — короткое резюме: что делает инструмент и что возвращает.

    Полный код инструмента grep

    import { tool } from "ai";
import { z } from "zod";
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join, relative, resolve } from "node:path";

const MAX_GREP_MATCHES = 50;

const grep = tool({
  description: `Search file contents using regex. Returns matching lines with file paths.

WHEN TO USE: finding patterns across multiple files, locating function definitions,
  searching for imports, finding TODOs or error messages.

WHEN NOT TO USE: reading a known file (use read instead).
  Running commands (use bash instead).

DO NOT USE FOR: reading files (use read), listing directories (use bash),
  modifying files (use edit).

EXAMPLES:
  - Find all TODO comments: pattern "TODO" glob "*.ts"
  - Find function definitions: pattern "function \\w+" glob "*.ts"`,
  inputSchema: z.object({
    pattern: z.string().describe("Regular expression to search for"),
    path: z.string().optional().describe("Directory to search (defaults to working directory)"),
    glob: z.string().optional().describe("Filter files by extension, e.g. \"*.ts\""),
  }),
  execute: async ({ pattern, path: searchPath, glob: globFilter }) => {
    const root = resolve(process.cwd(), searchPath ?? ".");
    const regex = new RegExp(pattern);
    const matches: string[] = [];

    function walk(dir: string): void {
      if (matches.length >= MAX_GREP_MATCHES) return;
      for (const entry of readdirSync(dir)) {
        if (matches.length >= MAX_GREP_MATCHES) return;
        const full = join(dir, entry);
        const stat = statSync(full);
        if (stat.isDirectory()) {
          walk(full);
          continue;
        }
        if (globFilter && !matchesGlob(entry, globFilter)) continue;
        if (stat.size > 1_000_000) continue; // пропускаем бинарные/огромные файлы
        const lines = readFileSync(full, "utf-8").split("\n");
        lines.forEach((line, i) => {
          if (matches.length >= MAX_GREP_MATCHES) return;
          if (regex.test(line)) {
            matches.push(`${relative(root, full)}:${i + 1}: ${line.trim()}`);
          }
        });
      }
    }

    walk(root);

    const header = matches.length >= MAX_GREP_MATCHES
      ? `Showing first ${MAX_GREP_MATCHES} matches (truncated):\n`
      : `Found ${matches.length} matches:\n`;

    return header + (matches.join("\n") || "(no matches)");
  },
});

function matchesGlob(filename: string, glob: string): boolean {
  // простое сопоставление по расширению: "*.ts" -> ".ts"
  const ext = glob.replace("*", "");
  return filename.endsWith(ext);
}

    📝 Перевод промта (поле description — что читает модель при выборе инструмента):

    «Ищи содержимое файлов по регулярному выражению. Возвращает совпавшие строки с путями к файлам.

    КОГДА ИСПОЛЬЗОВАТЬ: поиск паттернов по множеству файлов, нахождение определений функций, поиск импортов, нахождение TODO или сообщений об ошибках.

    КОГДА НЕ ИСПОЛЬЗОВАТЬ: чтение известного файла (используй read вместо этого). Запуск команд (используй bash вместо этого).

    НЕ ИСПОЛЬЗОВАТЬ ДЛЯ: чтения файлов (используй read), просмотра директорий (используй bash), изменения файлов (используй edit).

    ПРИМЕРЫ: - Найти все TODO-комментарии: pattern "TODO" glob ".ts" - Найти определения функций: pattern "function \w+" glob ".ts"»

    Разбор четырёх секций на этом примере

    Первая строка — резюме: «ищи по regex, возвращай строки с путями». Модель мгновенно понимает категорию инструмента (поиск), ещё до чтения секций.

    WHEN TO USE — перечисляет сценарии с ключевыми словами из реальных запросов: «finding patterns», «locating function definitions», «searching for imports», «finding TODOs». Когда пользователь пишет «найди все TODO», модель видит слово «TODOs» в этой секции и делает правильный выбор.

    WHEN NOT TO USE — мягкое перенаправление: «читаешь известный файл? — используй read». Обрати внимание, инструмент называется по имени (use read instead), а не описательно. Имя — это точный идентификатор, по которому модель найдёт нужный инструмент в своём списке.

    DO NOT USE FOR — жёсткий запрет: «никогда не используй для чтения файлов». Разница с предыдущей секцией — в тоне. WHEN NOT TO USE говорит «если твоя цель X, лучше возьми Y». DO NOT USE FOR говорит «этот инструмент НЕ для X, точка».

    EXAMPLES — конкретные вызовы с реальными значениями параметров. Модель не просто понимает назначение, а копирует показанный формат вызова. Это резко снижает число неправильно сформированных вызовов.

    Лимит 50 совпадений

    Заметь MAX_GREP_MATCHES = 50 и две вещи вокруг него:

    1. Ранний выход. Циклы walk и forEach проверяют matches.length >= MAX_GREP_MATCHES на каждой итерации и сразу выходят. Мы не обходим весь проект, если первые 50 совпадений уже найдены — экономим время и ресурсы.

    2. Видимое усечение. Если лимит достигнут, заголовок честно говорит модели: Showing first 50 matches (truncated). Модель знает, что есть ещё, и может уточнить поиск (сузить glob или pattern), вместо того чтобы принять неполный результат за полный.

    Почему именно 50? 50 совпадений достаточно, чтобы ответить на вопрос «где это используется». 500 совпадений — это уже дамп данных, который засоряет контекст без пользы. Это тот же принцип bounded output, что и в read с его 500 строками.

    Проверяем контракт в действии

    Сравни два запроса к агенту:

    // Правильный выбор: модель вызовет grep
await agent.run("Найди все места, где используется функция formatUser");

// Правильный выбор: модель вызовет read (известный конкретный файл)
await agent.run("Прочитай файл src/config.ts и скажи, что там");

    В первом случае ключевые слова «найди все места» совпадают с WHEN TO USE инструмента grep. Во втором — «прочитай файл X» совпадает с WHEN NOT TO USE у grep, что перенаправляет модель к read. Описание работает как сигнальный механизм маршрутизации.

    Ключевые выводы

    • Выбор инструмента — это задача маршрутизации. Как только инструментов больше одного, модель должна решать, какой подходит. Слабое описание = случайный выбор.
    • Bash gravity реальна. Все модели тяготеют к самому универсальному инструменту. Бороться с этим нужно не запретом, а сильными описаниями остальных инструментов.
    • 4-секционный контракт (WHEN TO USE / WHEN NOT TO USE / DO NOT USE FOR / EXAMPLES) превращает описание из фразы в инструкцию.
    • Негатив дублируется намеренно. WHEN NOT TO USE (мягко) и DO NOT USE FOR (жёстко) говорят одно и то же разной силой — чтобы покрыть модели разной мощности. Одного «не используй» почти всегда мало.
    • Называй инструменты по имени в секциях-перенаправлениях: use read instead, а не «используй инструмент чтения».
    • Примеры — это шаблон. Модель копирует формат вызова из EXAMPLES, а не изобретает свой.
    • Лимит 50 совпадений защищает контекст и делает усечение видимым, чтобы модель могла уточнить поиск.

    Попробуй сам

    1. Сравни слабое и сильное описание. Создай grep с описанием в одну строку "Search files." и попроси агента «найти все TODO». Затем замени на 4-секционный контракт и повтори запрос. Посмотри, как меняется выбор инструмента (в логах видно, какой инструмент вызван).

    2. Проверь гравитацию bash. Добавь к агенту read, grep и bash (пусть даже заглушку). Дай запрос «найди, где определена функция X». Заметь, как часто модель тянется к bash при слабом описании grep — и как перестаёт при сильном.

    3. Протестируй лимит. Создай проект с 200 вхождениями одного слова. Попроси агента найти их все через grep. Убедись, что вернулось ровно 50 совпадений и присутствует сообщение truncated.

    4. Проверь негатив. Дай запрос «прочитай файл src/index.ts». Правильное поведение — агент вызывает read, а не grep. Если он вызывает grep — усиль секции WHEN NOT TO USE и DO NOT USE FOR.

    5. Добавь свои примеры в EXAMPLES. Придумай третий реальный сценарий (например, поиск строки подключения к БД) и добавь его. Проверь, что модель начала успешнее справляться с этим типом запросов.
